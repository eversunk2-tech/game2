# Build 서브에이전트 지침: S1 쌓기나무 — 느린 기기에서 흔들리는 검사 고치기 (트랙 "blocks")

## 역할

너는 S1(쌓기나무 바탕 + 1·2차시)을 만든 **Build** 담당이다. 재검토는 "통과(반드시 수정 0건)"였지만, 코디네이터가 `main`에 합쳐 전체 테스트를 돌리다가 **브라우저 검사 1건이 지금 이 컴퓨터에서 늘 실패하는 것**을 찾았다. 앱 문제가 아니라 **검사가 움직임이 끝나기 전에 재는 문제**다. 이것과 같은 종류를 쌓기나무 검사 파일 전체에서 찾아 고친다. 검증은 별도 Review 서브에이전트가 다시 한다. `main`에는 이 문제가 풀릴 때까지 올리지 않는다.

## 찾은 문제 (코디네이터가 직접 잰 것 — 네가 다시 확인한다)

- `tests/e2e/net-workshop-blocks.spec.js`의 "정답 노출 0 (이쪽에서 보면?) …" 검사, 1106–1107행: 답을 누른 뒤 `.blk-option .blk-flat` 넷의 폭이 모두 같기를 기대하는데 `Expected: 1, Received: 2`. [chromebook]·[tablet] 모두, 혼자 돌려도 6번 중 6번 실패(트랙 폴더와 `main` 양쪽에서).
- 원인: 고른 보기에는 엔진이 `fx-correct`(`base.css` 508행 `animation: pop 0.35s`, 최대 `scale(1.08)`)를 붙인다. 답한 뒤 시간에 따른 보기 그림 폭: +0ms `[62, 62, 62, 62]` → +60ms `[64.33, 62, 62, 62]` → +150ms `[64.5, 62, 62, 62]` → +300ms부터 `[62, 62, 62, 62]`. 검사는 `is-answered` 클래스만 확인하고 바로 재므로, 재는 순간이 10ms 안이면 통과하고 20~280ms면 실패한다. 네 Build와 Review의 전체 실행에서는 우연히 통과했고(4번), 지금은 다른 일꾼들의 테스트로 컴퓨터가 느려 늘 실패한다. **느린 GitHub CI(리눅스)에서는 실패할 가능성이 높다.**
- 같은 날 엔진 검사에서도 같은 종류가 GitHub CI에서 실패했다(`engine-features.spec.js` "플레이 머리 높이 …": `.btn`에서 포인터를 뗀 뒤 1px 들뜸이 0.12초에 걸쳐 가라앉는 도중에 잼 — 따로 고치는 중이니 그 파일은 건드리지 않는다).

## 할 일

1. **그 검사를 고친다**: 답한 뒤의 크기·자리를 재기 전에 **보기들의 움직임(애니메이션·전환)이 끝날 때까지** 기다린다(예: `waitForFunction`으로 `.blk-options`의 `getAnimations({ subtree: true })`가 모두 끝났는지). 정해 둔 시간(`waitForTimeout`)으로 기다리지 않는다. **기대값은 그대로**(넷의 폭이 같다, 답하기 전보다 1.5배 넘게 작다, 한 줄에 넷) — 허용 오차를 넣거나 재는 항목을 빼지 않는다.
2. **같은 종류를 쌓기나무 검사 파일 전체에서 찾는다**: 누르기·답하기·포인터 올리기 **직후에** 요소의 크기·자리(`getBoundingClientRect`, `boundingBox`, `offsetWidth`가 아닌 변환이 반영되는 값)나 겹침·넘침·여유를 견주는 곳. 움직임의 종류: `fx-correct`(pop 0.35초)·`fx-wrong`(shake 0.4초), `.btn`의 들뜸·눌림 전환(0.12초), 알림(`toast-in` 0.2초), 화면이 들어오는 움직임, 쌓기나무 무대의 `.is-easing`(0.2초), 판·보기가 줄어드는 배치 바뀜. `fits()` 같은 배치 재기 도우미가 움직임을 기다리는지도 본다. 찾은 곳을 표로 보고하고(파일:줄, 무엇을 재는지, 어떤 움직임과 겹칠 수 있는지, 고쳤는지), **분명히 같은 문제인 곳만** 같은 방법으로 고친다. 공통 도우미 하나(예: `settled(page)`)로 묶어도 된다.
3. **느린 기기 흉내로 확인한다**: scratchpad에 푼 복사본(`git archive HEAD | tar -x -C <폴더>` + `node_modules` 링크)의 검사 파일 맨 위에 아래 같은 재현용 코드를 넣어 CPU를 느리게 하고 돌린다. **저장소의 검사 파일에는 재현용 코드를 남기지 않는다.**
   ```js
   test.beforeEach(async ({ page }) => {
     const rate = Number(process.env.SLOW_CPU || 0);
     if (!rate) return;
     const c = await page.context().newCDPSession(page);
     await c.send('Emulation.setCPUThrottlingRate', { rate });
   });
   ```
   - 고치기 **전**(`962e5fc`) 복사본: `SLOW_CPU` 0·4·8·12에서 `net-workshop-blocks.spec.js` 전체를 돌려 **느린 기기에서만 실패하는 검사 목록**을 만든다(시간 제한만 넘긴 것은 따로 표시 — 그것은 검사의 문제가 아니다).
   - 고친 **뒤**: 같은 배수에서 그 목록이 0인지, 고친 검사들은 `--repeat-each=8` 이상으로 실패 0인지.
   - 시간 제한에 걸리는 검사가 느리게 하기 탓인지는 혼자 다시 돌려 가린다. 시간 제한을 늘려 덮지 않는다(느리게 하기 실행에서만 `--timeout`을 명령줄로 늘리는 것은 된다).
4. 앱 코드(`src/**`)는 고치지 않는다. 느리게 하기에서 **앱이 실제로 잘못 동작하는 것**(검사가 아니라 화면이 틀리는 것)을 찾으면 고치지 말고 보고한다.

## 반드시 지킬 것

- 기존 검사를 지우거나 약하게 만들지 않는다. 기다림을 넣는 것 말고 기대값·재는 항목·장면 수는 그대로.
- 기다림이 끝나지 않을 길이 없는지 확인한다(끝없이 도는 애니메이션이 그 요소 안에 있으면 그것은 빼고 기다린다).
- 테스트: `npm test` + `npm run test:e2e -- --workers=4`(보통) + `E2E_WIDE_TEXT=font npm run test:e2e -- --workers=4`(글꼴 흉내)에서 실패 0. **지금 컴퓨터가 느린 상태 그대로에서도**(다른 일꾼이 돌고 있다) 실패 0이어야 한다 — 부하 탓으로 돌리지 않는다. 단, `tests/e2e/engine-features.spec.js`의 "플레이 머리 높이 …"가 `시간 재기를 끔`에서 실패하는 것은 따로 고치는 중이라 이 트랙의 실패로 세지 않는다(나오면 보고만).

## 고쳐도 되는 파일

- `tests/e2e/net-workshop-blocks.spec.js` 하나.
- 고치지 않는 것: `src/**`, 다른 테스트 파일, `tests/e2e/helpers.js`·`playwright.config.js`, `docs/**`(`review-blocks.md` 포함), `scripts/**`, package 파일, `.github/**`, `.claude/**`, `CLAUDE.md`

## 지킬 것

- 작업 폴더·브랜치·scratchpad는 지난번과 같다(코디네이터가 프롬프트로 다시 알려 준다). 지금 `track/blocks`의 HEAD는 `f440d9b`(코디네이터가 재검토 결과를 커밋했다)다. 커밋은 `track/blocks`에만, 푸시·합치기는 하지 않는다. 최종 상태는 커밋해 둔다.

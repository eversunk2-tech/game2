- 결과는 새 파일 `docs/games/net-workshop/review-cylinder-g3b.md` 하나다(트랙의 작업 폴더 안).
  - 맨 위에 판정 줄을 둔다: 통과 = 반드시 수정 0건 / 수정 필요.
  - 커밋하지 않는다.
- 금지:
  - 코드 · 테스트 · 다른 문서를 고치지 않는다.
  - 커밋하거나 작업 트리를 바꾸는 git 명령을 쓰지 않는다(읽기용은 된다).
  - `npm install` · `npm ci` · 내려받기를 하지 않는다.
- 서버 · 실행은 네가 띄운 PID만 내린다.
- 검증 파일은 정해 준 scratchpad에만 둔다.
- Build의 scratchpad는 근거로 삼지 않는다. 코디네이터가 고른 시안 그림 `build-g3b/shots/*.png`는 기준 모습으로만 쓴다.

- 기준: 지침을 맡긴 `main` 커밋(프롬프트로 알려 준다). 다른 화면은 이 빌드와 화소까지 같아야 한다.

- Build의 최종 보고는 코디네이터가 요약해 전한다. **확인 대상이지 근거가 아니다.**

## 확인할 것

1. **테스트**
   - `npm test`, `E2E_PORT=5363 npm run test:e2e -- --workers=4`를 보통과 글꼴 흉내로 직접, 하나씩 차례로 돌린다. 실패 0이어야 한다.
   - 바뀐 기존 `tests/`를 줄마다 읽는다. 뜻이 바뀐 줄(별 합계 · 도장 칸 수 등)만 바뀌었는지, 약해진 검사가 0인지 본다.
2. **계획 · 결정대로인가** — 코디네이터가 고른 시안 모습과 같은지 스크린샷을 직접 열어 견준다.
   - 3단계:
     - 카드 2문항 + 계산 2문항(또는 Build가 까닭을 대고 줄인 수)
     - 지름 카드 판마다 한 번
     - [굴려 재기]는 틀린 뒤에만
     - 계산: 숫자판, 틀린 값별 까닭 · tag, 두 번 틀리면 [힌트]
   - 숫자판: 0~9 · 소수점 · 지우기 · [확인하기] · 키보드, 입력 칸 길이 고정, "18.84" = "18.840"
   - 4단계:
     - 각기둥 4단계와 같은 판 · 손짓
     - 주문 3개 · 9가지 원기둥, 옆면 3장 + 원 두 묶음 ×2
     - 자석: 1 cm 안 · 접함 · 미끄러짐 · 끝에서 멈춤, 맞든 틀리든 같은 모습 · 소리
     - 옆면만 90° 돌리기
     - [말아 보기] 결과 다섯
     - 고른 까닭 먼저 → [펴서 고치기]
     - 2개면 끝 · 3개 ★3, 안 되게 말아도 별 안 깎임
     - 엇갈린 자리 쪽지
   - 도장 "원기둥 설계사" · 도장판 18칸
   - `?pi=` · 안내 한 줄, 놀이 방법 · 학습 기록 tag `원주 계산` · 별 합계 · 차시 칩
3. **독립 계산** — 저장소 코드를 쓰지 않고 기획서 문장만으로 짠다.
   - 대상: 4단계 판정(옆면 가로 = 지름 × 그 주문의 원주율, 원 반지름 = 주문, 마주 보는 두 변, 접점이 변 안, 엇갈린 자리는 됨), 3단계 계산 답(지름 2~6 × 3 · 3.1 · 3.14 손 계산 표)과 틀린 값의 까닭, 원주율 섞기(한 판 두 값 이상) · `?pi=`, 점수(처음 완성 +2 +5 · 이미 만든 것 0 · 안 되는 것 0 · 같은 원기둥 = 반지름 · 높이 같음), 별(완성한 수), 도장(여러 판 합침)
   - 무작위 모델 · 시드 수천 개로 견준다.
   - 일부러 틀려 이득 0, 화면 = 저장(새로 고침 · 나갔다 들어오기 · 탭 두 개)도 본다.
4. **정답 노출 0**
   - 3단계 카드 · 4단계 카드 · 원 묶음 · 숫자판에서 답하기 전 DOM을 본다: 속성 · 클래스 · `aria-*` · 화면 읽기 · 숨은 글 · DOM 차례 · 길이 글 규칙 · 원 묶음 모양.
   - 짐작 규칙("가장 긴 카드" · "가운데" · 묶음 모양 · 글 길이)의 정답률을 시드 3,000개 이상으로 직접 잰다. 3장 고르기는 찍기 33%보다 크게 높지 않아야 한다(높으면 규칙과 수치를 적는다).
   - 새 노출 검사가 노출을 일부러 넣은 복사본에서 실패하는지 직접 본다.
   - 자석이 맞는 · 틀린 · 다른 길이 · 짧은 변에서 같게 붙는지(모습 · 소리 · 알림) 본다.
5. **조작**
   - 키보드만 · 마우스만 · 터치만으로 3 · 4단계 끝까지 해 본다.
   - 48px, 누르기 · 끌기 8px를 본다.
   - 원 미끄러뜨리기 · 돌리기 · 판 옮겨 보기, 화면 읽기 문장 · 알림(알림이 조작을 가리지 않음), 움직임 줄이기 · `?fx=low`를 본다.
6. **배치** — **움직임이 끝난 뒤에** 잰다.
   - 크기: 1366×768 · 1366×680 · 1024×768 · 960×768 · 820×1180 · 390×844
   - 보통 · 글꼴 흉내 두 가지로 잰다.
   - 장면: 3 · 4단계 모든 장면, 단계 지도 · 학습 기록 도장판
   - 볼 것: 스크롤 · 넘침 · 겹침 0(휴대폰 세로 스크롤은 규칙대로), 판 → 무대 어긋남 0px, 9가지 원기둥의 맞는 전개도가 창 밖에 다 드는지
7. **그리기 · 속도**
   - 말기 · 굴려 재기 · 끌기의 프레임 간격을 CPU 1 · 4 · 8배로 직접 재서 Build 보고와 견준다.
   - 원주율 3일 때 원 크기(고른 방법)가 맞게 닫히는지 2배 화소로 확대해 본다.
   - 실물 기기는 "못 봄"으로 적는다.
8. **불변** — 기준 빌드와 견줘 다른 모든 화면이 같은지 본다.
   - 화면: 인트로 · 학년 · 영역 · 정육면체 · 직육면체 · 각기둥 1~4단계 · 도전 · 쌓기나무 1~5차시 · 도전 · 자유 쌓기(보통 · 큰 판) · **원기둥 1 · 2단계** · 학습 기록 · 선생님용 안내 · 예시 게임
   - **`magnet-board.js`를 고쳤다면 각기둥 4단계가 같은 시드 · 같은 조작에서 DOM · 화소 · 저장 값까지 같은지** 본다.
   - 의도한 차이만 있어야 한다: 원기둥 단계 지도 3 · 4단계, 별 합계, 도장 0 / 18 · 도장판 18칸, 놀이 방법 줄, 안내 `?pi=` 한 줄, 차시 칩.
9. **늦게 불러오기**: 새 코드가 원기둥 묶음에만 있는지 본다. 처음 받는 크기를 바뀌기 전과 뒤로 직접 잰다.
10. **느린 기기 검사**: 새로 만들거나 고친 검사를 CPU 4 · 8 · 12배로 돌린다. 값 실패 0이어야 한다.
11. **공개 저장소**: 교과서 문장 · 그림 · 문제 수치를 옮긴 곳이 없는지 본다(생활 장면 · 수 · 화면 글).
12. 새로 생긴 문제, 사용자가 정해야 할 것. 사용자가 자는 동안은 코디네이터가 정하므로 선택지와 추천을 붙인다.

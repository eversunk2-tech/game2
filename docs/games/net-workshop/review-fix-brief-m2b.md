# Review 서브에이전트 지침: 직육면체 차시 검토 반영 확인 (트랙 "cuboid")

## 역할과 범위

- 너는 **Review** 담당이다. Build가 [build-fix-brief-m2b.md](build-fix-brief-m2b.md)에 따라 고친 것을 **독립적으로** 확인하고, 지난 검토에서 통과한 것이 깨지지 않았는지 본다. Build와 분리된 검토자다.
- 트랙의 작업 폴더 안 `docs/games/net-workshop/review-cuboid.md` **한 파일만** 고친다: 맨 아래에 `## 재검토 (M2b 수정 확인)` 절을 덧붙이고, 맨 위 "판정"·"검토일" 줄을 고친다. 앞 내용은 지우지 않는다.
- 코드·테스트·다른 문서를 고치지 않는다. 커밋·브랜치 바꾸기·작업 트리를 바꾸는 git 명령 금지(읽기용은 된다). `npm install`·`npm ci` 금지.
- **트랙의 작업 폴더에서만** 일한다(코디네이터가 프롬프트로 알려 준다). `main` 체크아웃과 다른 트랙의 폴더는 건드리지 않는다(지침 파일을 읽는 것은 된다). 검증 파일·스크린샷은 정해 준 scratchpad 폴더에만. 개발 서버는 정해 준 포트만. e2e는 `--workers=4`.
- 옆 폴더 `review-m2/`에 지난 검토의 스크립트와 기준 빌드가 남아 있으면 **같은 스크립트로 다시 재서 지난 값과 나란히** 적는다(옛 복사본이 아니라 지금 작업 폴더를 새로 빌드한 것을 여는지 먼저 확인). 없으면 새로 짠다. Build의 scratchpad는 근거로 삼지 않는다.

## 기준

- `review-cuboid.md`의 문제 표(M2-1 ~ M2-11)와 그 측정값(지난 값)
- [build-fix-brief-m2b.md](build-fix-brief-m2b.md)의 **사용자 결정 3가지**(= [spec.md](spec.md) 16-14. 트랙 폴더의 spec.md에는 아직 없으니 `main` 체크아웃의 것을 읽는다)
- [common-rules.md](common-rules.md) 1~8절(`main` 체크아웃의 것이 최신이다)

## 검토 대상

기준 커밋 `4626338`(첫 Build, 지난 검토 대상)과 트랙 브랜치의 마지막 커밋 사이의 변경 전부(`b20a419`는 코디네이터가 review-cuboid.md만 커밋한 것이다). 커밋 안 된 것이 있으면 그것도 보고 그 사실을 적는다. Build가 고쳐도 되는 파일은 build-fix-brief-m2b.md의 목록이다. Build의 최종 보고는 코디네이터가 요약해 전한다 — **확인 대상이지 근거가 아니다.**

## 확인할 것

1. **테스트**: `npm test`, `npm run test:e2e -- --workers=4`를 보통과 글꼴 흉내(`E2E_WIDE_TEXT=font`)로 직접 실행(통과·실패·건너뜀). `git diff 4626338..HEAD -- tests/`로 **지워지거나 약해진 검사**가 없는지 — `cube-free`의 "3가지를 찾아야 끝난다"를 고친 검사는 새 결정(2가지면 끝낼 수 있음·3가지면 ★3)을 제대로 고정하는지.
2. **M2-1 (가장 중요)**: `cuboid-judge` 크기형 문항 — 시드 3,000개 이상에서 까닭 문장이 가리키는 두 면이 ⓐ 접었을 때 **실제로 마주 보는 면**이고 ⓑ 실제로 크기가 다른 면인지를, 저장소의 `fold.js`·`cuboid-logic.js`를 쓰지 않는 **독립 계산(직육면체 감싸기)**과 견준다(지난 값: 어긋남 466/3,000 = 15.5%, 그중 이웃 면 234). 겹침형·길이형 문장도 같은 방법으로. 정답·까닭 칩·tag·길이 띠가 여전히 맞는지. 화면에서 실제 문항 몇 개의 문장과 강조된 면을 스크린샷으로 직접 본다.
3. **점수 상한 (사용자 결정 2)**: 기획서 문장만 보고 짠 독립 계산 ↔ 엔진. ⓐ 54가지를 **순서를 섞어**(무작위 여러 벌) 찾은 총점이 모두 같은가, ⓑ 한 판에 몰아 찾기 / 여러 판에 나눠 찾기 / 도중에 나가기·새로 고침 / **탭 두 개**에서 "처음 10가지"의 경계가 흔들리지 않는가(10·11번째에서 두 번 받거나 못 받는 길 0), ⓒ 11번째부터 화면의 점수 안내(쪽지·알림·결과 화면)가 실제 +1과 맞는가, ⓓ 안 되는 것을 접거나 이미 찾은 것을 다시 접어 이득 0, ⓔ 화면 = 저장, ⓕ 정육면체 11가지의 점수는 그대로인가, ⓖ 54가지를 다 찾은 학생의 총점과 칭호 기준(300점). "찾은 전개도 n / 54"가 계속 오르는지.
4. **`cube-free` (사용자 결정 1 — 이미 사이트에 있는 단계를 일부러 바꾼 것)**: 2가지를 찾으면 [결과 보기]가 나오고 ★2, 더 찾아 3가지면 ★3, 결과 화면의 별 기준 안내. **그 밖에는 차이 0**: 기준 `3b48260` 빌드와 견줘 3가지를 찾는 판의 화면·점수(33점)·기록이 같은지, 1가지만 찾고는 끝낼 수 없는지. `cuboid-free`도 같은 기준인지. 도감 주문(`cube-dex`)은 그대로인지.
5. **정육면체 차시 불변**: 기준 `3b48260` 빌드와 견줘 `cube-judge`·`cube-opposite`·`cube-complete`·`cube-dice`·`cube-dex`의 화면(글자·속성·자리·크기)·점수·기록·답하기 전 화면 차이 0(지난 검토의 6,470장면 비교를 다시). 정육면체 판정을 독립 계산과 다시 견줌(M2-9로 `fold.js`를 고쳤으므로).
6. **그 밖의 항목을 하나씩**: M2-2(띠 이름표 — 처음 시점과 돌려 본 자세 여러 개에서 거꾸로·옆으로·거울상인 것의 수. 지난 값: 판별 48개 중 바로 선 것 11, 선분 120개 중 50), M2-3(접은 장면에서 "겹쳐요"·띠 이름표와 길이 글자의 포개짐 — 지난 값 36개 중 34), M2-4(전체 차시 수·"모은 별 n / 24"에 기대는 검사가 남았는지 — **쌓기나무 트랙 `track/blocks`의 마지막 커밋과 `git merge-tree`나 임시 복사본으로 합친 나무에서** 단위·브라우저 검사를 돌려 보면 좋다. 실제 작업 폴더는 건드리지 않는다), M2-5(`?lesson=cuboid`의 머리·내 공방 카드, `?lesson=cube`·차시를 고르지 않은 화면·예시 게임 불변), M2-6(힌트가 아직 찾지 않은 전개도를 먼저 보이는지), M2-7(만나는 선분 정답 자리 분포·알맞은 카드의 크기 순위 분포를 시드 1,000개 이상으로 — 지난 값 넷째 30.7%·가장 작은 카드 21.8%), M2-9.
7. **깨지지 않았는가(지난 스크립트로 다시, 지난 값 → 지금 값)**: 직육면체 판정 ↔ 독립 계산 불일치 0(54가지·29가지·만나는 선분·마주 보는 면·길이·겹침), 답하기 전 정답 노출 0(네 단계, 찍기 통계 포함 — 보기 자리를 바꿨으므로 다시), 직접 만드는 단계의 규칙(예상 관련 말 0, 안 되는 것을 접어도 별이 깎이지 않음), 세 크기 세로·가로 스크롤 0·판 넘침 0·잘린 버튼 0·머리와 매트 움직임 0·판 → 무대 0px, 48px, 보기 조작(끝없이 돌리기·조작판은 답한 뒤만), 끄는 면 보임·끈 직후 탭, 콘솔 오류 0, 나간 뒤 리스너·타이머 0.
8. **느린 기기에서 흔들리는 검사**(수정 지침의 "덧붙임 (2026-10-12)" 절): scratchpad에 푼 복사본의 검사 파일 맨 위에 CPU 느리게 하기(`Emulation.setCPUThrottlingRate`)를 넣어 4·8·12배로 이 트랙의 검사 파일(`net-workshop-cuboid.spec.js`, `net-workshop-free-finish.spec.js`, `net-workshop.spec.js`)을 돌린다. **느린 기기에서만 실패하는 검사 목록**(시간 제한만 넘긴 것은 따로 표시)이 0인지, Build가 넣은 기다림이 기대값을 약하게 하지 않았는지(`toEqual`·허용 오차·재는 항목), `waitForTimeout`으로 덮지 않았는지, 끝나지 않는 기다림이 없는지. 답하기·누르기 직후에 크기·자리를 재는 곳을 훑어 Build가 놓친 곳이 있는지. 저장소의 검사 파일에 재현용 코드가 남지 않았는지. (`engine-features.spec.js`의 "플레이 머리 높이 …"는 트랙 "c1"이 따로 고친다 — 이 트랙에서 실패해도 이 트랙의 문제로 세지 않는다.)
9. **범위·합치기**: 허용 파일 안인지. 엔진(`src/shared/**`)에서 고친 곳의 줄 목록과 타당성, 예시 게임 불변. 같이 쓰는 파일에서 쌓기나무 트랙과 줄 단위로 부딪히는 곳(`git merge-tree`).
10. **새로 생긴 문제**, 사용자가 정해야 할 것(선택지와 추천).

## 형식과 끝나면

덧붙이는 절: 판정 줄, 테스트 결과 표, 항목별 결과 표(M2-번호 · 지난 값 → 지금 값 · 고쳐짐/남음), 점수 상한 표, 느리게 하기 배수별 결과 표, 새로 발견한 문제 표(심각도: 반드시 수정 / 고치면 좋음 / 참고, 파일:줄, 재현 방법, 고칠 방향), 깨지지 않았는지의 표, 확인하지 못한 것.

최종 답변 **12줄 이하**: 판정(통과 / 수정 필요), M2-1(어긋남 수/표본), 점수 상한(순서·판 나눔·탭 두 개·경계), `cube-free`가 달라진 것과 달라지지 않은 것, 정육면체 다섯 단계 불변 수치, 나머지 항목 요약, 깨지지 않았는지의 핵심 수치, 테스트 숫자(보통·글꼴 흉내), 새 문제와 심각도별 개수, "반드시 수정" 목록(파일:줄), 합칠 때 부딪힐 곳, 확인하지 못한 것. 직접 잰 것과 추정을 구분한다.

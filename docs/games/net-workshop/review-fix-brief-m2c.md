# Review 서브에이전트 지침: 직육면체 차시 — 검사 파일 손질 확인 (트랙 "cuboid", M2c)

## 역할과 범위

- 너는 **Review** 담당이다. Build가 [build-fix-brief-m2c.md](build-fix-brief-m2c.md)에 따라 고친 **검사 파일 셋**을 **독립적으로** 확인한다. Build와 분리된 검토자다. 앱 코드는 지난 재검토(`15cf985`, 통과 — 이미 `main`에 올라가 사이트에 있다)에서 달라지지 않았어야 한다.
- 트랙의 작업 폴더 안 `docs/games/net-workshop/review-cuboid.md` **한 파일만** 고친다: 맨 아래에 `## 재검토 2 (M2c 검사 손질 확인)` 절을 덧붙이고, 맨 위 "판정"·"검토일" 줄을 고친다. 앞 내용은 지우지 않는다. 커밋하지 않는다.
- 코드·테스트·다른 문서를 고치지 않는다. 커밋·브랜치 바꾸기·작업 트리를 바꾸는 git 명령 금지(읽기용은 된다). `npm install`·`npm ci`·내려받기 금지.
- **트랙의 작업 폴더에서만** 일한다(코디네이터가 프롬프트로 알려 준다). 검증 파일·복사본은 정해 준 scratchpad 폴더에만. Build의 scratchpad는 근거로 삼지 않는다.

## 검토 대상

`15cf985`(지난 재검토 대상)와 트랙 브랜치의 마지막 커밋 사이의 변경 전부(`4126bfc`는 코디네이터가 review-cuboid.md만 커밋한 것). **바뀐 코드 파일은 `tests/e2e/net-workshop-cuboid.spec.js`·`tests/e2e/net-workshop-free-finish.spec.js`·`tests/e2e/net-workshop.spec.js`(시간 예산 한 줄) 셋뿐이어야 한다** — `src/**`가 한 줄이라도 바뀌었으면 범위 위반이다. Build의 최종 보고는 코디네이터가 요약해 전한다 — **확인 대상이지 근거가 아니다.**

## 확인할 것

1. **범위**: `git diff 15cf985..HEAD --stat`. `tests/e2e/net-workshop.spec.js`의 변경이 "자유 배치: 모든 장면…"의 예산 한 줄뿐인지. 저장소의 검사 파일에 재현용 코드가 남지 않았는지. `15cf985`와 지금 것으로 각각 빌드한 `dist/*.html` 세 파일의 해시가 같은지.
2. **M2b-1(550ms만 보이는 "반 접힘")**: `15cf985` 복사본에서 실패가 재현되는지(누른 뒤 600ms 늦추기, 또는 CPU 4·8배를 컴퓨터가 바쁠 때), 지금 것의 복사본에서 4·8·12배 × `--repeat-each=12` 이상으로 실패 0인지(두 기기). 고친 검사가 본래 뜻("움직임 줄이기에서는 펼침 → 반 접힘 → 다 접힘으로 넘어가고 접는 움직임은 없다")을 그대로 고정하는지 — 복사본의 앱에서 반 접힘 장면을 건너뛰게, 또는 접는 움직임(`folding`)이 나오게 망가뜨리면 실패하는지.
3. **같은 종류로 더 고친 곳 (꼼꼼히)**: Build가 지침의 표에 없던 곳을 더 고쳤다 — 힌트의 반 접힘(1.4초)과 그동안 숨는 꼭짓점 이름, 몇 초 뒤 사라지는 알림 글 4곳("뜬 글을 적어 두고 견줌"), 화면 읽기 알림을 기다리던 고정 60ms("알림 글이 들어온 뒤에 봄"). `git diff 15cf985..HEAD -- tests/`를 줄마다 읽어 **각각이 검사를 약하게 만들지 않았는지** 판단한다: 기대하는 글·값이 그대로인지, "지나간 값을 적어 두고 본다"가 "한 번이라도 나왔으면 통과"로 느슨해져 놓치는 회귀가 생기지 않았는지(예: 알림이 엉뚱한 때에 뜨거나, 틀린 글이 떴다가 맞는 글로 바뀌는 경우), 적어 두는 관찰이 누르기보다 **먼저** 시작되는지, 관찰이 다음 문항으로 새지 않는지. 표본으로 앱을 망가뜨려(알림 글을 바꿈, 힌트의 반 접힘을 없앰, 꼭짓점 이름을 숨기지 않음) 그 검사들이 실패하는지.
4. **시간 예산(M2b-2·3)**: 예산 말고 바뀐 것이 없는지. 표본으로 혼자 돌린 시간(보통·CPU 4배)을 재서 Build의 표와 견주고, 예산이 4배 시간의 3배 이상인지(900초로 올린 "자유 배치: 모든 장면…"은 지침이 정한 값), 지나치게 크지 않은지. 예산이 없는데 3초 넘게 걸리는 검사가 이 두 파일에 남았는지.
5. **M2b-8**: `toContainText('도감 0 / ')`로 돌아왔는지, 쌓기나무와 합친 지금의 `main`에서도 그 글이 맞는지(읽기만 — `main`의 그 화면 글을 코드나 빌드로 확인).
6. **느리게 하기 전체**: 지금 것의 복사본에서 이 트랙의 검사 파일 둘을 4·8·12배로 한 번씩 — 값이 어긋나는 실패 0인지(시간 제한만 넘긴 것은 따로 표시).
7. **합칠 때**: 지금의 `main`(`origin/main`)·`track/c1`의 지금 커밋과 `git merge-tree --write-tree`로 합쳐 보아 줄 충돌이 없는지(읽기만).
8. **테스트**: `npm test`, `npm run test:e2e -- --workers=4`, `E2E_WIDE_TEXT=font npm run test:e2e -- --workers=4`를 직접 실행(통과·실패·건너뜀). 이 가지에는 `c1`·`c2`의 수정이 없어 **전부터 흔들리던 기존 검사**(`engine-features.spec.js` "플레이 머리 높이 …", `net-workshop.spec.js`의 "주사위 주문 배치" 등)가 컴퓨터가 바쁠 때 실패할 수 있다 — 이 트랙의 문제로 세지 않되 목록으로 적는다. **이 트랙의 두 검사 파일에서 나온 실패는 부하 탓으로 넘기지 않는다.**
9. **새로 생긴 문제**.

## 형식과 끝나면

덧붙이는 절: 판정 줄(통과 = 반드시 수정 0건 / 수정 필요), 테스트 결과 표, 느리게 하기 배수별 결과 표(`15cf985` → 지금), 더 고친 곳마다의 판단 표(약해졌는가 · 회귀를 잡는가), 시간 예산 표(표본), 발견한 문제 표(심각도, 파일:줄, 재현 방법, 고칠 방향), 확인하지 못한 것.

최종 답변 **8줄 이하**: 판정, M2b-1(기준과 지금, 회귀를 잡는지), 더 고친 곳의 판단, 시간 예산, M2b-8, 빌드 해시, 느리게 하기 전체 결과, 합칠 때 부딪힐 곳, 테스트 숫자, 새 문제와 심각도별 개수, "반드시 수정" 목록(파일:줄), 확인하지 못한 것. 직접 잰 것과 추정을 구분한다.

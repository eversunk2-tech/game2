## 3. 크기 상한

모두 scratchpad에 푼 복사본(`git archive` + `node_modules` 링크)과 임시 폴더의 시험용 게임으로 직접 확인했다.

- **ⓐ 400 KB를 넘는 게임**: 템플릿으로 만든 시험용 게임에 진짜 PNG(480×480 잡음 그림, 691,958바이트)를 CSS `url()`로 넣었다.
  - 지금 것: 빌드됨. `✓ dist/big-game.html  (1031.6 KB, 제목 글꼴 333자 27.2 KB)`. 알려 주는 크기 = 실제 크기 = 1,056,407바이트, 바깥 참조 0, 넣은 그림이 원본과 바이트까지 같음.
  - 기준: `big-game: 파일이 1031.6 KB로 상한 400.0 KB를 넘어요.`로 멈춤.
  - 그 파일을 테스트용 크롬(Chromium, 화면 없이, 1366×768, `file://`)으로 열었다: 제목 "큰 게임 시험", 큰 그림이 480×480으로 풀림, 제목 글꼴 `loaded`, [시작하기] → 단계 2개 → 플레이 화면, 콘솔·페이지 오류 0, 바깥 요청 0. 처음 화면 스크린샷을 직접 열어 봄.

### ⓒ 검사의 뜻 — 그대로다

- 검사 본문(177행~)에서 `timerSettled`가 들어간 줄과 주석 두 줄을 빼면 기준과 **한 글자도 다르지 않다**(`diff`로 확인). `expect(` 25개 → 25개, `toEqual(start)` 5개 → 5개. 재는 항목 일곱(머리·뒤로·제목·목표·시간 재기·솜씨 점수·무대)과 0.01px 반올림, 네 크기 × 두 단계, 장면 순서도 같다. 허용 오차는 넣지 않았다.
- 넣은 줄: 195–197행(도우미), 234행(켬 — `.timer-label`만 기다리던 줄을 버튼과 그 안 전체로 넓힘), 243행(끔), 248행(다시 켬). `waitForTimeout` 없음.
- **기다림이 끝나지 않을 길은 찾지 못했다**: 버튼과 그 안에 걸리는 움직임은 유한한 전환 셋(120ms·200ms·120ms)뿐이다. `src/**`에 `infinite` 0건, 반복하는 것은 `turn-hint`(0.9초 × 4번, 다른 버튼)뿐. 시계 글자(`.timer-clock`)는 버튼의 형제라 기다림의 대상이 아니다. **움직임 줄이기 설정**(`reducedMotion: 'reduce'`)으로 6배에서 6번 돌려 6번 통과, 기다림은 가장 길어야 16ms.
- 기다림이 가리는 것은 버튼 자신의 0.2초짜리 움직임뿐이다. 그 움직임(`transform`·`background-color`)은 다른 요소의 자리를 바꾸지 않는다. "켬"은 기준에서도 글자의 움직임이 끝나기를 기다린 뒤 쟀다.

## 10. 확인하지 못한 것

- **리눅스 CI의 실제 통과** — `main`에 올린 뒤에만 알 수 있다. 여기서 한 것은 이 맥에서 CPU를 느리게 한 흉내와 기기 부하다. 글꼴 흉내도 CI의 글꼴 그 자체는 아니다.
- 느리게 하기 전체 실행은 배수마다 **한 번**씩이다. 드물게만 실패하는 검사는 더 있을 수 있다(A는 8배 전체 실행에서는 통과했고 그 검사만 되풀이했을 때 1 / 10이었다). 2배·32배 등 다른 배수는 돌리지 않았다.
- 찾기 도구는 검사 코드가 `page.evaluate` 안에서 `getBoundingClientRect`로 잰 것만 본다. `locator.boundingBox()`로 잰 곳과 `toBeInViewport`는 잡지 못한다(그 가운데 `:519–522`만 따로 재 보았다).
- 기기 부하가 클 때 보통 실행의 실패 0은 세 번째에야 얻었다. 다른 일꾼들의 테스트가 같은 때에 돌았기 때문이며, 실패한 것은 모두 혼자 다시 돌려 통과를 확인했다.
- 400 KB를 넘는 파일이 GitHub Pages에 올라가 열리는 것(이 맥의 `file://`로만 열어 봄), 실물 크롬북·태블릿, Safari.
- 다른 두 트랙(직육면체·쌓기나무)을 합친 뒤의 빌드(약 421 KB)는 이 검토의 대상이 아니다.

### ⓒ 검사의 뜻 — 그대로다

- 검사 본문(177행~)에서 `timerSettled`가 들어간 줄과 주석 두 줄을 빼면 기준과 **한 글자도 다르지 않다**(`diff`로 확인). `expect(` 25개 → 25개, `toEqual(start)` 5개 → 5개. 재는 항목 일곱(머리·뒤로·제목·목표·시간 재기·솜씨 점수·무대)과 0.01px 반올림, 네 크기 × 두 단계, 장면 순서도 같다. 허용 오차는 넣지 않았다.

- **기다림이 끝나지 않을 길은 찾지 못했다**: 버튼과 그 안에 걸리는 움직임은 유한한 전환 셋(120ms·200ms·120ms)뿐이다. `src/**`에 `infinite` 0건, 반복하는 것은 `turn-hint`(0.9초 × 4번, 다른 버튼)뿐. 시계 글자(`.timer-clock`)는 버튼의 형제라 기다림의 대상이 아니다. **움직임 줄이기 설정**(`reducedMotion: 'reduce'`)으로 6배에서 6번 돌려 6번 통과, 기다림은 가장 길어야 16ms.

### 알림 확인을 "누른 바로 뒤"로 옮긴 것 — 접힌 뒤의 화면을 놓치는가

- 앱의 알림은 띄울 때 한 번 자리를 정하고(`feedback.js:100` `place()`), 창 크기가 바뀔 때만 다시 정한다. `position: fixed`라 그 뒤 화면이 접혀도 알림은 움직이지 않는다. 그래서 "접힌 뒤에 알림이 조작을 가린다"는 **조작 쪽이 접힌 뒤에 알림 자리로 들어올 때만** 생긴다.
- 직접 잰 것(`probe-now`, 1배, 네 크기, 알림 자리를 보는 곳 모두 — 누른 바로 뒤로 옮긴 6곳 포함): 알림 확인이 끝난 순간과 다 접힌 뒤(약 1.1초 뒤 — 그때도 알림은 떠 있다)의 조작 버튼을 견줬다. **개수는 같고**, 달라지는 것은 접기 버튼의 너비(넓은 화면·태블릿 136 → 103px, [접어 보기] → [펴기])와 그 옆 막대의 왼쪽 끝(같은 만큼 왼쪽으로)뿐이다. 휴대폰은 바뀌는 것이 없다. 다 접힌 뒤에도 알림과 겹치는 조작은 0, 가장 가까운 조작과의 틈은 16~24px. → **Build의 설명이 맞고, 지금 앱에서는 놓치는 경우가 없다.**
- 다만 검사는 이제 접힌 뒤의 화면을 보지 않는다. 일부러 "다 접힌 뒤에만 조작 띠가 알림 자리로 60px 움직이게"(`.free-mat:has(.fold-stage[data-fold="done"]) .fold-tools`) 망가뜨리면 옮긴 세 검사(1·2·3번)의 알림 확인은 이것을 보지 못하지만, **이 파일의 다른 검사가 잡는다**: "겹치는 모양과 2×2 모양…"(보통·움직임 줄이기·fx=low × 두 기기 = 6개, 다 접힌 뒤 알림 자리를 본다 `:1378` → `:88`), "주사위 주문 배치"의 겹침 확인(`:2760`, 크롬북), "판 → 무대 이어 접기 0px"(`:5469`, 크롬북). 그래서 지금은 빈틈이 아니고 참고로 적는다(c2-4). 더 단단히 하려면 누른 바로 뒤에 읽은 알림 자리를 적어 두었다가 다 접힌 뒤의 조작과 한 번 더 견주면 된다(알림이 그때 떠 있지 않아도 된다).

### 새로 찾은 앱의 흔들림 — 끌기 안내가 가끔 안 남는다 (c2-1)

- 지금 것의 6번 검사가 **두 번** `:3830`(`.view-tip`이 보여야 하는데 숨김)으로 실패했다: CPU 4배·부하 37의 여섯 검사 실행에서 크롬북 10번 중 1번, 그리고 CPU 1배·부하 11~21의 `net-workshop.spec.js` 전체 실행(조작 띠를 망가뜨린 빌드 — 그 망가뜨림은 `.free-mat`에만 걸려 면 붙이기와 무관)에서 1번. 그 줄은 이번에 바뀌지 않은 뒷부분(면 붙이기)이고 `d6371ad`와 글자까지 같다. 지금 검사의 크롬북 6번 실행은 이 검토에서 모두 약 170번(확인용 사본 포함, 1·4·8·12·16배, 부하 5~80)이고 그중 2번이다. 기준 검사 28번에서는 나오지 않았다 — 드물게만 난다. 태블릿에서는 한 번도 나오지 않았다.
- 실패한 실행의 기록(trace)의 화면을 직접 열어 보았다: 틀린 자리를 누른 바로 뒤 화면(5,341ms)에는 "끌어서 돌려 봐요" 안내가 **보이고**, 16ms 뒤(5,357ms)에는 **사라져** 끝까지 다시 나오지 않는다. 접는 움직임은 정상으로 끝났다.
- 원인(코드와 실험으로 확인): `src/games/net-workshop/view3d.js:639` 접는 움직임의 진행도 `p = Math.min(1, (now - start) / ms)`에 아래쪽 한계가 없다. 첫 프레임의 시각 `now`(프레임이 시작된 때)는 누른 처리 안에서 잰 `start`보다 **앞설 수 있고**, 그러면 `p`가 음수인데 `ease(p) = 2p²`(`:106`)는 양수라 접는 정도 `t`가 0 → 작은 양수 → (다음 프레임이 `start` 근처면) 1e-6 이하 → 다시 양수로 **오르내린다.** `t > 1e-6`일 때만 켜지는 "보기 조작 됨"(`can-view`)이 켜졌다 꺼졌다 켜지고, 안내는 처음 켜질 때 한 번만 보이게 되어 있어(`:1106-1118` `tipUsed`) 꺼질 때 숨은 채로 남는다.
- **결정적으로 재현**(`probe-nm/` — 같은 앱을 줄이지 않고 빌드, 검사 쪽에서 `requestAnimationFrame`의 시각만 바꿈): 첫 프레임을 `start − 10ms`, 둘째를 `start + 0.5ms`로 주면 안내가 "보임 → 숨김"이 되고 다 접힌 뒤에도 숨어 있다(실제 시각을 그대로 주면 보임 유지). 실패한 기록과 같은 모양이다. 다시 5번씩 돌려도 같다(바꾼 시각 5/5 숨김, 그대로 5/5 보임).
- 영향: 느린 기기에서 드물게 학생에게 "끌어서 돌려 봐요"가 안 보인다(기능은 그대로). 검사 쪽으로는 이 안내를 단언하는 `:3830` · `:4105`가 GitHub CI에서 드물게 흔들릴 수 있다. 이번 c2가 만든 것이 아니고 앱 코드라 c2의 범위 밖이다.

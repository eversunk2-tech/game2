# 계획: 쌓기나무 판을 알지오매스처럼 돌리기 · 넓은 판의 "자유 쌓기" (spec-grade6 15-18)

> 2026-10-18 Plan 서브에이전트. 지침 [plan-brief-rotate.md](plan-brief-rotate.md)(덧붙임 "5학년 전개도는 그대로" 포함) + 코디네이터가 알려 준 사용자 결정 **"쌓기나무 판의 돌리기만 수정해줘."** → 새 돌리기는 **쌓기나무 무대(놀이터·차시 단계·자유 쌓기)에만** 쓰고, 전개도 입체(5학년 정육면체·직육면체, 6학년 각기둥 — 원기둥은 나중)는 **화면·동작 한 글자도 그대로** 둔다. 그래서 "6학년 전개도에도 쓸지"는 묻지 않고, 전개도 쪽 시제품·비교 그림도 만들지 않았다.
> 저장소 코드는 고치지 않았다. 시제품·측정·스크린샷은 모두 scratchpad `plan-rotate/`에 있다(맨 끝 10절).
> **직접 본 것·잰 것**과 **추정**을 갈라 적는다. 추정에는 "(추정)"을 붙인다.

## 1. 한 문단 요약

알지오매스의 돌리기를 헤드리스 Chromium으로 직접 끌어 보니 **돌림판식**이었다: 가로로 끌면 판이 자기 세로축 둘레로 제자리에서 돌고, 세로로 끌면 내려다보는 높이만 바뀌며(바로 위 ~ 바로 아래에서 멈춤), 판의 세로축은 어떻게 끌어도 화면에서 곧게 섰다(바로 위·아래가 아닌 마우스·터치 장면 20여 장에서 기움 0.1° 안). 돌기의 중심은 **판 가운데로 늘 같았고 누른 자리와 무관**했다(누른 곳 네 군데에서 같은 끌기 → 화면이 화소 하나까지 같음). 지금 우리 쌓기나무 무대는 화면 기준으로 구르는 트랙볼식(`orbit.js`, spec 17-17)이라, 비스듬히 내려다보는 처음 보기에서 가로로 120px만 끌어도 탑이 **31.5°** 기울고, 학생이 주로 가로로 몇 번 끄는 흉내 2,000판에서 기울기 가운데값 **29.4°**, 30° 넘게 기운 판 **48.6%**, 판 밑에서 보게 된 판 **44.7%**였다. 새 규칙은 쌓기나무 무대만 **돌림판식**(가로 = 판 돌리기, 세로 = 내려다보는 높이, 기울기 0°)으로 바꾸고, `orbit.js`·`view3d.js`는 한 줄도 고치지 않는 새 모듈로 만든다(시제품에서 같은 끌기를 나란히 견준 그림: `shots/cmp-all.png`). 자유 쌓기는 쌓기나무 단계 지도의 **1차시 위에 놓인 넓은 카드 한 장**(차시 번호·별·잠금 없음 — 사용자 결정)이다. 판은 사용자 결정대로 **알지오매스와 같은 14×14칸**(직접 세어 확인 — 쌓기나무 하나 = 한 칸, 높이 한도는 30층까지 없음, 판 밖에는 놓이지 않음)에 10층까지, **휴대폰은 6×6칸·6층**. 처음 보기에 판이 꽉 차게 맞추면 크롬북에서 쌓기나무 한 변 34~36px, 오른쪽 "위에서 본 판"은 네 쪽(7×7, 48px)으로 나눈다. "판의 절반을 3층"(294개)을 돌려도 CPU 6배 느리게 한 실행에서 프레임 34ms 넘음 0이었다. 쌓기·빼기·되돌리기·모두 치우기·새 돌리기·[위][앞][옆]·개수·층별로 벌려 보기 + 색 고르기·위·앞·옆에서 본 모양을 넣고, 점수 없이 **판 크기마다 이 기기에 하나 자동 저장**하는 안을 추천한다. Build는 **R1(돌리기) → F1(자유 쌓기)** 두 번으로, 지금 Review 중인 S3(쌓기나무 5차시)가 합쳐진 뒤 그 위에서 한다. 사용자 결정이 넷(돌리기 중심·위아래 한도·카드 모양·판 크기) 나왔고, 남은 물음은 셋(7절).

**정리 — 알지오매스 돌리기의 정체**: (1) 가로 = 판의 세로축 둘레 돌리기(끝없이), (2) 세로 = 내려다보는 높이(바로 위 ~ 바로 아래에서 멈춤), (3) **세로축이 화면에서 늘 곧다**(옆으로 구르지 않음 — 사용자가 말한 "수평이 맞게"), (4) 돌기의 중심은 판 가운데로 고정, 오른쪽 끌기로 판을 옮기면 옮긴 자리가 새 중심, (5) 1px ≈ 0.28°(캔버스 너비 ≈ 한 바퀴), 관성 없음, 휠은 판 가운데 기준, (6) 보기 상자로 앞·옆·위에 바로, "원점복귀(0)", (7) 판은 **14×14칸**(쌓기나무 하나 = 한 칸), 높이 한도는 30층까지 보이지 않음, 판 밖에는 놓이지 않음. 웹 3D에서 흔한 "궤도 돌리기(orbit)"와 같은 동작이다(추정 — 코드를 보지 않았다).
**"내가 선택한 지점 중심으로"**는 재 본 바로는 "누른 곳이 돌기의 중심이 된다"가 아니었다. 사용자가 느낀 것은 (가) 판이 기울지 않아 내가 보는 곳이 화면에서 안정되게 도는 느낌이거나 (나) 오른쪽 끌기로 옮긴 자리를 중심으로 도는 것일 수 있다(추정). → 사용자 결정: 판 가운데를 중심으로(7-1절 1).

## 3. 지금 쌓기나무 판이 기우는 까닭 (B — 계산으로 잼)

**까닭.** 지금 쌓기나무 무대는 `orbit.js`의 `dragView`(spec 17-17)를 그대로 쓴다(`block-view.js:682`). 끈 방향과 직각인 **화면 위의 축** 둘레로 굴리는 트랙볼식이다. 그런데 쌓기나무의 처음 보기는 교과서 그림처럼 **35.3° 위에서 비스듬히** 내려다보는 자세라, 화면의 세로축과 판의 세로축이 54.7° 어긋나 있다. 가로로 끌면 판은 자기 세로축이 아니라 **화면 세로축** 둘레로 돌고, 그러면 판의 세로축이 원뿔을 그리며 옆으로 눕는다(쌓기나무의 세로 모서리가 기운다). 여러 번 끌면 화면 기준 회전은 순서를 바꿀 수 없어(교환되지 않아) 기울기가 쌓인다. S1-13(review-blocks.md)이 "가로 60°(120px)에 31°"라고 적은 것과 같은 현상이다.

**판의 기울기**(쌓기나무 세로 모서리가 화면 위쪽에서 기운 각도)를 저장소의 `orbit.js`·`block-view.js` 함수 그대로 계산했다(`proto/tilt.mjs`, 끌기를 4px씩 나눠 적용 — 실제 `pointermove`처럼).

### 4-2. 바뀌지 않는 것 (정답 노출·잠금)

- 답하기 전 잠금(멈춘 그림, 조작판·방향 버튼 숨김 — 5절·17-16)은 **그대로**다. 바뀌는 것은 "돌릴 수 있을 때 어떻게 도는가"뿐이라 새로 드러나는 것이 없다. 돌림판식으로 갈 수 있는 자세는 지금 갈 수 있는 자세의 일부다(판 밑·기운 자세가 빠질 뿐).
- 멈춘 그림·단계 카드 그림(`createBlockPicture`, `POSES.home`)은 그대로 — 처음 보기 행렬이 같다.
- 답하기 전 화면이 문항과 무관하게 한 가지 모습이라는 검사, [위][앞][옆] 뒤 2D 그림과 겹치는 검사(`overlay`)는 뜻이 그대로다.

### 4-3. 전개도 쪽이 바뀌지 않게 하는 방법 (설계)

- **새 순수 모듈 `src/games/net-workshop/blocks/turn-view.js`**(이름은 Build가 정해도 됨): `poseOf(yaw, pitch)`(3×3 행렬), `HOME`·`SNAP`(위·앞·옆·뒤·왼쪽·behind의 `{ yaw, pitch }`), `homeTurn`, `dragTurn(view, dx, dy)`, `stepTurn(view, dir, step)`(눈금), `turnToward(a, b, f)`(움직임 잇기), `turnLimits(view)`(`up`·`down`·`zoomMax`·`zoomMin`·`home`), `PITCH_MIN`·`PITCH_MAX`.
- `block-view.js`는 회전 함수만 이 모듈에서 가져오고(보기 값을 `{ yaw, pitch, zoom }`으로, `poseOfRoll`·`rollTo`는 `poseOf`·`SNAP`으로), **배율·휠·벌리기·문턱·움직임 길이·말**(`stepZoom`·`wheelView`·`pinchView`·`DRAG_START`·`MIX_MS`·`zoomWord`·`HOME_WORD`·`clamp`)은 지금처럼 `orbit.js`에서 가져온다(모두 `zoom`만 다루는 순수 함수라 그대로 맞다).
- **`orbit.js`·`view3d.js`·`play-*.js`(전개도)·`cuboid-*`·`grade6/*`는 0줄 변경.** Review는 `git diff main -- src/games/net-workshop/orbit.js src/games/net-workshop/view3d.js`가 비었는지, 전개도 e2e(`net-workshop.spec.js`·`-cuboid*`·`-prism`)가 바꾸지 않고 통과하는지로 확인한다.
- 시제품은 같은 결과를 "orbit.js와 같은 이름의 함수를 돌림판식으로 바꿔 끼운" 껍데기(`proto/turntable.mjs`)로 만들었다 — `block-view.js` 사본의 import 한 줄과 버튼 두 줄만 바꿔 돌아갔다(`proto/block-view-tt.js`). 실제 Build는 위처럼 보기 값을 `yaw`·`pitch`로 두는 쪽이 깔끔하다(사원수 ↔ 각도 변환이 필요 없음).

- 같은 기기에서 판 크기가 달라지는 때(창을 아주 작게 줄여 연 경우, 태블릿을 나눠 쓴 화면 등)를 위해 **판 크기마다 따로 하나씩** 남긴다(열쇠 `free-14x14`, `free-6x6`). 14×14에서 쌓은 것을 6×6 판에 들어오면 6×6의 것(없으면 빈 판)이 보이고, 다시 큰 화면에서 들어가면 14×14의 것이 그대로 있다 — 잘리거나 지워지는 일이 없다.
- 고르지 않은 안: 하나만 남기고 작은 판에서는 가운데 6×6만 보여 주기(바깥 칸을 고칠 수 없고 "모두 치우기"가 보이지 않는 칸까지 지우는 문제), 판을 바꿀 때마다 옮겨 담기(바깥 칸이 사라짐).

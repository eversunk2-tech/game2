# 기획서: 6학년 영역 — 각기둥의 전개도 · 원기둥의 전개도 · 쌓기나무

> 게임 id: `net-workshop` · 상태: **승인됨 (2026-10-09, 결정은 15절)** · 지침: [plan-brief-grade6.md](plan-brief-grade6.md) · 바탕 기획서: [spec.md](spec.md)
>
> spec.md 1~17절과 결정 표는 그대로 두고, 이 문서는 6학년 영역이 더하거나 바꾸는 것만 적는다. "5학년 완성"(N2 도전 주문서, 2차 직육면체 — spec 14절·16-2·16-5)은 이미 승인된 계획이라 다시 계획하지 않는다.
>
> 교과서 세 단원(6-1 2단원, 6-2 3단원, 6-2 6단원)을 모두 처음부터 끝까지 읽고 썼다(0절). 처음 쓴 판에서 "임시안"이던 쌓기나무·원기둥은 교과서에 맞춰 **확정안**으로 고쳤고, 무엇이 왜 바뀌었는지는 2-3·2-4·3-8절에 적었다. 사용자가 이미 정한 것은 15절에 있다.

**요약**

- **교과서(세 단원 모두 직접 읽음)**: 6-1 2단원 29~54쪽, 6-2 3단원 53~74쪽, 6-2 6단원 119~138쪽. 세 단원 모두 "먼저 예상 → 직접 만들어(접어·쌓아) 확인 → 까닭 말하기"로 짜여 있어 이 게임의 뼈대와 맞는다.
- **쌓기나무 단원(6-2 3단원)은 5차시**다: 어느 방향에서 보았는지(56~57쪽) → 만든 모양과 위에서 본 모양(58~59) → 위·앞·옆에서 본 모양(60~63) → 위에서 본 모양에 수 쓰기(64~65) → 층별로 나타내기(66~67). 2~5차시의 줄기는 "똑같이 만드는 데 필요한 쌓기나무의 개수"다. "옆"은 오른쪽이고, 모눈은 3×3칸·3층까지이며, 위층은 아래층이 있는 자리에만 놓인다(66쪽) — **뜬 쌓기나무가 없다는 사용자 결정과 같다.** "쌓기나무 몇 개로 여러 가지 모양 만들기"는 이 단원에 없다.
- **원기둥(6-2 6단원)**: 원기둥 알아보기(122~123쪽) → 원기둥의 전개도(124~127쪽: 펼친 모양 → 될 수 있는 것 찾기 → 옆면의 가로·세로 → 그리기). 원뿔·구에는 전개도 활동이 없다. **원주율의 값은 이 단원 쪽에 적혀 있지 않다**(13절 1번).
- **앱 구성**: 같은 앱("입체도형 공방")에 영역 셋 — 5학년 전개도 / 6학년 전개도(각기둥 4단계, 원기둥 4단계) / 쌓기나무(**교과서 차시와 하나씩 짝지은 5차시 15단계 + 도전 1**).
- **쌓기나무 조작**: 판(**3×3칸, 3층까지** — 교과서 모눈과 같은 크기)에 직접 쌓고·빼고·돌려 본다. 짧게 누르면 쌓기·빼기, 누른 채 8px 넘게 끌면 돌리기(쌓는 중에도 된다). [위] [앞] [옆] 버튼은 그 방향에서 본 모습으로 돌려 주고, 원근 없는 그리기라 2D 그림과 똑같이 보인다. 뜬 쌓기나무는 없다(아래로 내려앉음).
- **그리기 방식(시제품으로 잼)**: 쌓기나무는 직접 투영 SVG(깊이 순서 오류 0, 느린 CPU 흉내에서도 60프레임, 누르기 판정이 정확), 각기둥·원기둥은 지금의 CSS 3D 무대를 넓힘(원기둥 옆면 = 띠 36개). WebGL·Three.js는 쓰지 않는다. 교과서를 읽은 뒤에도 바뀌지 않았다.
- **빌드 구조**: 여러 파일 + 이름에 해시 + 영역을 들어갈 때 불러오기(B0). 주소는 그대로다. 잰 값: 지금 248 KB(gzip 102 KB), 다 넣어도 약 368 KB(gzip 약 148 KB, 추정)이고, JS를 82 KB 키운 시제품은 6배 느린 CPU에서 처음 화면이 0.30초(지금 0.32초)였다.
- **Build**: B0 + 6번(쌓기나무 S1~S3 → 각기둥 G1~G2 → 원기둥 G3), 각각 Review 한 번. 순서는 15절 결정 그대로.
- **사용자에게 확인할 것은 하나**: 원기둥 문제에서 원주율을 얼마로 계산하게 할지(13절). 나머지는 15절에서 이미 정해졌다.

직접 확인한 사실(계획에 쓰는 것)

- 전개도 차시에 나오는 각기둥: **삼각기둥**(38·40·43쪽), **사각기둥**(41쪽), **육각기둥**(41쪽). 판별 보기(39·52쪽)에는 삼각형·사각형·오각형·육각형 밑면이 섞여 있다. 단원 전체로는 팔각기둥이 이름으로 한 번 나온다(53쪽).
- 그리기 활동의 밑면은 정다각형만이 아니다(40쪽 직각이 있는 삼각형, 41쪽 직사각형이 아닌 사각형). → spec 9절의 "밑면이 정다각형이 아닌 각기둥은 하지 않음"을 이 문서가 바꾼다(2-2절).
- 판별 보기에는 옆면이 한 줄 띠로 이어지지 않은 그림도 있다(39·52쪽). → spec 1-1절의 "각기둥은 옆면 띠 + 밑면 2개 꼴만"을 "띠 꼴이 기본, 낯선 꼴 한 가지를 섞는다"로 바꾼다.
- **각뿔의 전개도 활동은 이 단원에 없다**(44~47쪽은 뜻·구성 요소·이름뿐). spec 15절 결정(각뿔 제외)과 맞는다.

직접 확인한 사실(계획에 쓰는 것)

- **차시의 줄기**: 2~5차시는 제목이 같고(만든 모양과 쌓기나무의 개수) 나타내는 방법만 바뀐다 — 위에서 본 모양 → 위·앞·옆 → 수 쓰기 → 층별. 뒤로 갈수록 "모양과 개수가 하나로 정해지는" 방법이다. 처음 계획의 3차시 나눔(여러 방향에서 보기 / 개수와 수 / 층별·여러 가지 모양)과 다르다.
- **문제의 크기**: 2D 모눈은 모두 3×3칸 안, 층은 3층까지, 쌓기나무는 열 개 안팎이다.
- **방향을 알려 주는 방법**: 입체 그림에서는 "앞"이 왼쪽 아래, "옆"이 오른쪽 아래에 화살표로 적혀 있다. 위에서 본 모양 모눈에는 아래쪽에 "앞", 오른쪽에 "옆"이 붙는다. 2차시(58~59쪽)만 위에서 본 모양을 입체 그림과 같은 방향으로 비스듬히 놓아 그렸다.
- **뜬 쌓기나무는 없다**: 위에서 본 모양을 "바닥에 닿은 면의 모양"으로 보는 것(58·63쪽)과 66쪽 귀띔이 모두 그 전제다. 15절 3번 결정과 부딪히는 활동이 없다. "보이지 않는 쌓기나무"는 뜬 것이 아니라 **가려진 자리가 몇 층인지**의 문제다.
- **"같은 모양"의 약속(돌리거나 뒤집어 같으면 같은 모양)과 "쌓기나무 몇 개로 여러 가지 모양 만들기"는 이 단원에 없다.** 54쪽에 앞서 배운 내용의 이름으로만 나온다.
- 60·64·66쪽에 쌓기나무 공학 도구를 쓰라는 안내가 있다 — 화면에서 쌓기나무를 다루는 활동이 교과서 흐름 안에 자리가 있다.
- 1차시는 쌓기나무가 아니라 실제 장면으로 "보는 방향"을 다룬다.

별 기준은 모든 단계가 엔진 기본(정답률 90%↑ ★3, 70%↑ ★2, 틀린 시도도 셈). 시간·횟수는 별에 쓰지 않는다.
끝나는 조건(표에 따로 적지 않은 단계): 판별·예상만 하는 단계는 문항을 모두 답하면, 고르기·칠하기·쌓기 단계는 문항을 모두 맞히면(맞힐 때까지 다시 하고 틀린 시도도 기록), 여러 가지를 찾는 단계는 목표 가지 수를 찾고 [결과 보기]를 누르면 끝난다. 실패 조건·시간 제한은 없다.
시간은 문항당 어림(고르기 25~35초, 칠하기·수 쓰기 35~55초, 쌓기 45~80초)으로 계산했다. 실제 학생 시간은 재지 못했다 — Build 뒤 손으로 재서 문항 수를 고친다.

- 시간: 3 × 25~35초 + 5 × 25~35초 + 3 × 25~35초 + 자유 배치 3~4분 + 단계 사이 1분 = **8.6~11.4분.**

- **전개도 그리기를 화면에서**: 교과서의 "모눈에 이어 그리기"를 **면 카드를 모서리에 붙이기**로 옮긴다(spec 16-2의 `prism-free` 방식 그대로: 카드를 고르면 빈 모서리마다 48px "붙일 자리"가 생긴다). 그리는 솜씨가 아니라 정리 ①~④(면의 수, 직사각형, 겹침, 길이)를 스스로 지키는지가 드러난다. 옆면 카드는 가로가 서로 다르므로(밑면의 변 길이만큼) 길이가 안 맞는 모서리에 붙이면 접었을 때 "5 cm ≠ 3 cm"처럼 보인다. 자와 연필로 그리는 활동 자체는 종이 교과서의 몫으로 남긴다.
- spec 5절의 얼개(`prism-sides` → `prism-judge` → `prism-length`)에서 바뀐 것: 옆면 [−][+] 맞추기와 길이 고르기를 따로 두지 않고, 교과서 순서대로 "밑면·옆면 찾기 → 판별 → 맞닿는 선분 → 완성하기"로 묶었다. 옆면의 수는 판별의 안 되는 보기와 완성하기의 카드 한 벌로, 길이는 맞닿는 선분과 완성하기로 다룬다.

- **원주율**: 교과서 이 단원에 값이 없으므로(1-3절) 화면이 알려 줘야 계산할 수 있다. 계산이 필요한 문항(`cylinder-size` 뒤 2문항, `cylinder-free`의 카드 길이)에는 "원주율: 3.1"처럼 값을 문제 문장에 적는다. 어떤 값을 쓸지는 13절 1번. 1·2단계와 3단계 앞 2문항은 계산 없이 풀린다(말아 보기, 굴려 재기).

- **`cylinder-free`의 "일부러 안 되게"**: 되는 꼴이 사실상 한 가지라(spec 16-2) 예상이 뜻을 가지려면 안 되는 것도 만들어 봐야 한다. 교과서 127쪽의 확인 물음 둘(면이 맞는가 / 맞닿는 부분의 길이가 같은가)을 **직접 어겨 보고 왜 안 되는지 확인하는** 활동으로 옮긴 것이다. 원 카드에는 크기가 다른 원이, 옆면 카드에는 가로가 지름만큼인 것이 섞여 있다.

- **1차시를 쌓기나무 무대로 옮긴 방법**: 교과서 1차시는 실제 장면이다. 앱은 삽화를 따로 그리지 않고 **색과 높이가 다른 쌓기나무 조형물 셋**(예: 노랑 3층 탑, 파랑 2층, 빨강 1층)이 놓인 판을 쓴다. "가까운 것이 먼 것을 가린다", "반대쪽에서 보면 좌우가 바뀐다"는 같은 생각을 다루고, 답한 뒤 그 방향으로 직접 돌려 확인할 수 있다. 네 방향의 모습이 모두 다른 배치만 낸다.
- **도전 `blocks-add`의 "같은 모양"**: 이 단원 교과서에는 돌리거나 뒤집은 모양을 같은 모양으로 보는 약속이 글로 나오지 않는다(1-2절). 그래서 보기는 **놓인 방향이 같은 것만** 낸다(판을 돌리지 않고 겹쳐 볼 수 있음). 돌려야 같은 보기는 내지 않는다.
- 짝 활동으로 쓰는 법(코드 없음, spec 4-1): 같은 `?seed=`로 `blocks-layer-draw`를 한 학생이, `blocks-layer-build`를 짝이 하면 교과서 놀이(70~71쪽)와 같은 흐름이 된다.

### 2-5. 지금 정육면체 차시와 어떻게 이어지나

| 정육면체 차시의 흐름 | 각기둥 | 원기둥 | 쌓기나무 (차시마다 같은 흐름) |
| --- | --- | --- | --- |
| 판별 (예상 → 접어 확인 → 까닭) | `prism-judge` | `cylinder-judge` | 예상 → 돌려서·벌려서 확인 → 까닭: `blocks-where`, `blocks-count`, `blocks-flip` |
| 구조 이해 (마주 보는 면) | `prism-parts`, `prism-edge` | `cylinder-parts`, `cylinder-size` | 나타내기: `blocks-draw`, `blocks-write`, `blocks-layer-draw` |
| 만들기 (한 면 붙이기) | `prism-free`의 첫 과제 | `cylinder-size`의 감기 | 보고 쌓기: `blocks-copy`, `blocks-build`, `blocks-fromnum`, `blocks-layer-build` |
| 내 맘대로 (여러 가지 찾기) | `prism-free`의 둘째 과제(다른 모양으로) | `cylinder-free` | 여러 가지로 쌓기: `blocks-hidden`, `blocks-build`의 끝 문항, 도전 `blocks-add` |

- 뼈대는 모든 영역에서 같다: **먼저 머릿속으로 → 화면에서 확인 → 까닭.** 전개도는 "접어서(말아서) 확인", 쌓기나무는 "돌려서·벌려서 확인"이다. 사용자가 좋다고 한 단계 구성과 돌려 보기를 그대로 잇는다.
- 다른 점 하나: 쌓기나무의 쌓는 단계는 **쌓는 동안에도 돌려 볼 수 있다**(3-3절). 만든 것이 곧 답이라 돌려 봐도 답이 드러나지 않는다(5절).

### 3-3. 누르기(쌓기)와 끌기(돌리기)를 가르는 방법

- **8px 문턱**(지금 `orbit.js`의 `DRAG_START`와 같은 값): 누른 곳에서 8px 넘게 움직이면 돌리기, 그 전에 떼면 누르기. 돌리기가 시작되면 점선 쌓기나무는 사라지고 아무것도 놓이지 않는다. 뗄 때 따라오는 `click`은 한 번 삼킨다(지금 무대와 같은 처리).
- 지금 전개도 무대는 "답한 뒤에만 돌리기"로 누르기와 끌기가 부딪히지 않게 했다. 쌓기나무는 그럴 수 없으므로 **때가 아니라 움직인 거리로** 가른다. 터치에서는 누르는 동안 점선 쌓기나무가 먼저 보이므로, 잘못 눌렀으면 끌어서(돌리기로 바뀜) 취소할 수 있다.
- 끌기가 어려운 학생(크롬북 터치패드): 돌리기는 조작판·방향키·[위][앞][옆]으로, 쌓기는 "위에서 본 판"으로 모두 할 수 있다. **끌지 않고도 모든 조작이 된다.**
- 무대의 `touch-action`: 쌓는 단계의 무대는 늘 `none`(한 손가락 = 돌리기, 두 손가락 = 크게·작게). 휴대폰에서 페이지를 내리려면 무대 밖(주문서·여백)을 쓴다 — 무대 높이를 화면의 절반 이하로 잡아 쓸 자리를 남긴다.
- 답하기 전에 돌리면 안 되는 문항(5절)은 입체 대신 멈춘 그림을 보여 주고, 조작판과 방향 버튼을 숨긴다(지금 전개도 무대의 잠금과 같은 모습).

### 3-4. "위·앞·옆에서 본 모양"을 화면에서 보여 주는 방법

- **원근 없는 그리기(평행 투영)**를 쓴다. [앞]을 누르면 0.2초 동안 그 방향으로 돌아가고, 다 돌면 화면의 쌓기나무가 **앞에서 본 모양 그림과 똑같은 네모들**로 보인다. 원근이 있으면 뒤쪽 쌓기나무가 작게 겹쳐 보여 2D 그림과 달라진다(전개도 무대는 원근 1100px 그대로 둔다). 교과서의 입체 그림도 원근 없이 그려져 있다.
- **"옆"은 오른쪽**이다(교과서 60쪽). [옆]은 오른쪽에서 본 모습으로 돌린다. `blocks-flip`에서만 [뒤]·[왼쪽]이 더 나와 "뒤집으면 같다"를 직접 본다.
- 주문서의 2D 그림(위·앞·옆)은 같은 크기 3×3 모눈에 칸을 칠한 그림이다. 답한 뒤에는 그림을 누르면 무대가 그 방향으로 돈다(그림과 입체를 잇는 다리).
- 확인 장면: 무대가 그 방향을 보는 동안 2D 그림을 무대 위에 반투명 테두리로 겹쳐 준다. 다른 칸은 빗금 + ✗ + "여기가 달라요"(색만으로 알리지 않음).
- 움직임 줄이기·`?fx=low`: 돌아가는 움직임 없이 바로 그 방향이 된다.

### 3-5. 교과서 활동과 잇는 방법

| 교과서 활동 (쪽) | 직접 하는 조작 | 확인하는 방법 | 단계 |
| --- | --- | --- | --- |
| 어느 방향에서 본 모습인지 찾기 (56~57) | 화살표 고르기 → 답한 뒤 직접 돌려 봄 | 그 방향으로 돌아가 그림과 겹침 | `blocks-where`, `blocks-scene` |
| 그림만 보고 똑같이 만들기 (58) | **쌓고·빼고·돌려 보며** 만든다 | 내 것을 그림과 같은 쪽에서 본 모습과 견줌. 같아 보이는 다른 쌓기를 보여 줌 | `blocks-copy` |
| 그림 + 위에서 본 모양으로 개수 구하기 (58~59) | 개수 고르기 | **층별로 벌려 보기**: 층이 위아래로 벌어져 숨겨진 쌓기나무가 드러나고 층마다 개수가 뜬다 | `blocks-count` |
| 개수가 여러 가지인 까닭 (59, 61) | 같은 그림에 맞게 두 가지로 쌓기 | 두 쌓기를 나란히 돌려 보고, 달라진 자리를 표시 | `blocks-hidden`, `blocks-build` |
| 다섯 방향에서 본 모양, 뒤집으면 같은 것 (60) | 보기 고르기 → [앞][뒤][오른쪽][왼쪽]으로 돌려 봄 | 두 방향의 모습을 나란히 놓고 좌우로 뒤집어 겹침 | `blocks-flip` |
| 위·앞·옆에서 본 모양 그리기 (60, 62~63) | 모눈 칸을 눌러 칠함 | 무대가 그 방향으로 돌아가 내 그림과 견줌 | `blocks-draw` |
| 위·앞·옆을 보고 만들기 (61) | 쌓기 | 세 그림과 견줘 다른 칸 표시 | `blocks-build` |
| 위에서 본 모양에 수 쓰기 (64~65) | 돌려 보며 자리마다 수를 올리고 내림 | 자리마다 쌓기나무가 아래부터 반짝이며 수와 견줌 | `blocks-write` |
| 수를 보고 만들기, 수만 보고 앞·옆 그리기 (64~65) | 쌓기 / 칠하기 | 자리마다 수와 견줌 / 입체가 나타나 그 방향으로 돎 | `blocks-fromnum`, `blocks-numviews` |
| 층별 모양 그리기 · 층별 모양을 보고 만들기 (66~67, 70~71) | 층 모양 칠하기 / 쌓기 | 층별로 벌려 보기 + 층 그림과 겹침 | `blocks-layer-draw`, `blocks-layer-build`, `blocks-layer-views` |
| 쌓기나무를 더 붙여 만들기 (68~69) | 보기 고르기 → 직접 붙여 봄 | 붙인 모양과 보기를 겹침 | `blocks-add` |

### 3-6. 실물 쌓기나무와 다른 점

| 다른 점 | 어떻게 다루나 |
| --- | --- |
| **뜬 쌓기나무** | **없다 (15절 3번 결정).** 놓으면 아래로 내려앉고, 빼면 맨 위 것이 빠진다. 교과서도 같은 전제다(위에서 본 모양 = 바닥에 닿은 면의 모양, 아래층이 빈 자리에는 위층을 둘 수 없음 — 58·63·66쪽). 그래서 만든 모양은 늘 "자리마다 몇 개"로 나타낼 수 있고, 이것이 곧 4차시의 수 쓰기다 |
| 가려진 뒤쪽 | 실물은 몸을 움직여 본다 → 화면은 돌려 본다. 교과서가 "그림을 보고" 하는 활동은 멈춘 그림으로 내고, 답한 뒤 돌려 보기·층별로 벌려 보기를 연다 |
| 붙여서 든 모양 | 실물은 붙이지 않으면 들어 올릴 수 없지만 화면은 통째로 돈다 |
| 크기·무게감 | 판 가장자리의 "앞"·"옆" 글자와 바닥 모눈으로 자리 감각을 돕는다 |
| 손끝으로 세기 | 답한 뒤 쌓기나무를 누르면 그 자리의 수가 뜬다("이 자리는 3개") |

### 3-7. 판 크기·최대 높이·최대 개수

| 값 | 정한 것 | 까닭 |
| --- | --- | --- |
| 판 | **3×3칸** | 교과서의 모눈이 모두 3×3칸 안이다(1-2절). 2D 그림과 판의 칸 수가 같아 그대로 견줄 수 있다 |
| 최대 높이 | **3층** | 교과서가 3층까지만 다룬다(층별 모양도 1·2·3층) |

## 4. 오개념 표와 피드백

`tag`는 학습 기록에 그대로 남는 말이다. 같은 개념은 5학년 차시의 tag(spec 3절)를 이어 쓰고, 새 tag만 굵게 적는다.

| 영역 | tag | 학생의 생각 | 만나게 하는 방법 | 틀렸을 때 "왜"를 보여 주는 방법 (문장 예) |
| --- | --- | --- | --- | --- |
| 각기둥 · 원기둥 | **밑면은 바닥 면** | 바닥에 닿은 면이 밑면이다 | `prism-parts`·`cylinder-parts`에 눕힌 것을 늘 1개 | 고른 두 면이 서로 평행하지 않음을 입체에서 보여 줌. "밑면은 서로 평행하고 모양과 크기가 같은 두 면이에요. 놓인 방향과는 상관없어요." |
| 각기둥 | 옆면 수 = 밑면 변 수 | 옆면은 늘 4개다 | `prism-judge`의 안 되는 보기, `prism-free` 카드 | 접으면 한쪽이 비거나(점선 "비어요") 겹침. "밑면이 오각형이면 변이 5개라서 옆면도 5개예요." |
| 각기둥 · 원기둥 | **옆면은 직사각형** | 옆면이 기울어진 사각형이어도 된다 | `prism-judge`·`cylinder-judge`의 안 되는 보기 | 밑면과 맞닿을 두 변의 길이가 다름을 같은 무늬와 길이로 표시. "원기둥의 옆면을 펼치면 직사각형이에요. 위아래 변의 길이가 달라서 두 밑면에 맞지 않아요." |
| 각기둥 · 원기둥 | 두 밑면의 위치 | 두 밑면을 같은 쪽에 붙여도 된다 | 판별에 늘 1개 | 접으면(말면) 두 밑면이 같은 자리에 겹침(빗금 "✗ 겹쳐요"), 반대쪽은 "비어요" |
| 각기둥 · 원기둥 | 두 밑면은 합동 | 두 밑면의 크기가 달라도 된다 | 판별, `cylinder-free`의 원 카드 | 접으면 한쪽 밑면이 옆면과 안 맞음 |
| 각기둥 | 맞닿는 모서리 길이 | 길이가 비슷하면 붙는다 | `prism-judge`, `prism-free`(가로가 다른 옆면 카드) | 맞닿아야 할 두 선분을 같은 무늬로 칠하고 "5 cm ≠ 3 cm" |
| 각기둥 | 만나는 선분 | 전개도에서 가까운 선분끼리 맞닿는다 | `prism-edge` 보기에 바로 옆 선분 | 접는 장면에서 두 선분이 같은 무늬로 만남 |
| 각기둥 · 원기둥 | 여러 가지 전개도 | 늘 보던 꼴만 전개도다 | `prism-judge`·`cylinder-judge`의 낯선 꼴, `prism-free`의 "다른 모양으로" | "이 모양도 말면 원기둥이 돼요. 두 밑면이 옆면의 위와 아래에 하나씩 있으면 자리는 달라도 돼요." |
| 원기둥 | **높이** | 비스듬한 길이나 밑면의 지름을 높이로 고름 | `cylinder-parts`의 높이 문항 | 두 밑면 사이에 곧게 선 자를 대어 보여 줌. "높이는 두 밑면 사이의 거리예요." |
| 원기둥 | 옆면 가로 = 밑면 둘레 | 옆면의 가로는 지름(반지름)이다 | `cylinder-size` 카드에 지름, `cylinder-free`의 옆면 카드 | 말면 틈이 생김 + [굴려 재기]. "옆면의 가로는 밑면의 둘레와 같아요. 지름만큼으로는 한 바퀴를 못 감아요." |
| 원기둥 | 옆면 세로 = 높이 | 세로를 밑면의 길이와 헷갈림 | `cylinder-size` | 말린 원기둥의 높이와 옆면 세로를 같은 무늬로 |
| 쌓기나무 | **보는 방향** | 반대쪽에서 봐도 좌우가 그대로다 / 가려지는 것을 생각하지 못한다 | `blocks-where`·`blocks-scene` 보기에 맞은편에서 본 모습 | 고른 방향으로 먼저 돌아간 뒤 바른 방향으로 돎. "나 쪽에서 보면 노란 탑이 오른쪽에 있어요. 이 그림은 맞은편에서 본 모습이에요." |
| 쌓기나무 | **보이지 않는 쌓기나무** | 보이는 것만 센다 | `blocks-count`에 숨겨진 쌓기나무가 있는 모양을 늘 2개 | 층별로 벌려 보기: 숨겨졌던 쌓기나무에 점선 테두리 + "숨어 있었어요". "1층에 5개, 2층에 2개, 모두 7개예요." |
| 쌓기나무 | **바닥에 닿은 면** | 위에서 본 모양의 칸 수가 곧 개수다 / 위에서 본 모양에 없는 자리에 쌓는다 | `blocks-count` 보기에 위에서 본 모양의 칸 수, `blocks-hidden`·`blocks-build` | "위에서 본 모양은 바닥에 닿은 면의 모양이에요. 자리는 5곳이지만 2층, 3층에도 쌓여 있어요." |
| 쌓기나무 | **개수가 여러 가지** | 그림이 같으면 쌓기나무의 개수도 하나로 정해진다 | `blocks-hidden`, `blocks-build`의 끝 문항의 예상 | 같은 그림에 맞는 두 쌓기를 나란히 돌려 보여 주고 달라진 자리를 표시. "이 자리는 다른 쌓기나무에 가려서 1층이어도 2층이어도 똑같아 보여요." |
| 쌓기나무 | **앞과 옆** | 앞에서 본 모양과 옆에서 본 모양을 바꿔 그린다(고른다) | `blocks-draw`, `blocks-numviews`, `blocks-layer-views` | 무대가 그린 방향으로 먼저 돌아간 뒤 바른 방향으로 돎. "이 그림은 옆에서 본 모양이에요. 판의 '앞' 글자 쪽에서 봐야 해요." |
| 쌓기나무 | **좌우 뒤집힘** | 뒤(왼쪽)에서 본 모양이 앞(오른쪽)과 똑같다 / 옆에서 본 모양을 좌우로 뒤집어 그린다 | `blocks-flip` 보기, `blocks-draw`의 옆 문항 | 두 그림을 겹쳐 뒤집힌 줄을 표시. "뒤에서 보면 앞에서 본 모양이 좌우로 뒤집혀요." |
| 쌓기나무 | **가장 높은 층** | 앞에서 보면 줄마다 맨 앞 쌓기나무의 높이만큼 보인다고 생각 | 앞줄이 낮고 뒷줄이 높은 모양 | 그 세로줄만 남기고 나머지를 흐리게 → 뒤의 높은 쌓기나무가 보임. "앞에서 보면 세로줄마다 가장 높은 층까지 보여요." |
| 쌓기나무 | **수의 뜻** | 위에서 본 모양의 수를 층 번호나 순서로 읽는다 | `blocks-write`, `blocks-fromnum` | 그 자리의 쌓기나무가 아래부터 하나씩 반짝이며 셈. "이 수는 그 자리에 쌓인 쌓기나무의 개수예요." |
| 쌓기나무 | **층별 모양** | 2층 모양에 1층에만 있는 자리를 넣는다 / 층을 헷갈린다 | `blocks-layer-draw` | 층별로 벌려 그 층만 남김 |
| 쌓기나무 | **위층은 아래층 위에** | 아래층에 없는 자리에 위층을 칠한다 | `blocks-layer-draw`, `blocks-layer-views` | 그 자리에 놓으려던 쌓기나무가 아래로 내려앉는 장면. "아래층이 비어 있으면 위층에 놓을 수 없어요." |
| 쌓기나무 | **더 붙인 모양** | 한 개를 붙여서는 만들 수 없는 모양을 고른다 | 도전 `blocks-add` | 처음 모양을 보기 위에 겹쳐 남는 쌓기나무를 표시. "이 모양은 2개를 더 붙여야 해요." |

- 쌓는 단계의 피드백은 "틀렸어요"가 아니라 **어디가 다른지**다: 그림 가운데 맞은 것에는 ✓, 다른 것에는 다른 칸 표시. tag는 가장 먼저 어긋난 그림으로 정한다(위에서 본 모양이 다르면 `바닥에 닿은 면`, 앞·옆이 서로 바뀐 꼴이면 `앞과 옆`, 그 밖에 앞이나 옆이 다르면 `가장 높은 층`).
- 힌트(쌓는 단계): 같은 문항을 두 번 틀리면 [힌트] — 위에서 본 모양의 자리 하나에 수를 보여 준다. 힌트를 써도 별·점수는 그대로(spec 16-1과 같은 원칙).
- 까닭 고르기(원기둥 판별): 보기는 교과서 127쪽 확인 물음의 말(밑면이 합동인 원 2개가 아니에요 / 옆면이 직사각형이 아니에요 / 두 밑면이 같은 쪽에 있어요).

## 5. 답하기 전 정답 노출 검토

원칙은 지금과 같다: **답이 기록되기 전에는 화면이 답을 알려 주지 않는다.** 쌓기나무는 "돌려 보면 답이 보이는 문항"과 "돌려 보는 것이 곧 과제인 문항"을 갈라야 한다. 교과서가 "그림을 보고" 하게 한 활동은 멈춘 그림으로, "쌓기나무로 만들어 보고" 하게 한 활동은 돌릴 수 있는 판으로 나눴다.

| 단계 | 답 | 답하기 전 돌려 보기 | 까닭 · 지키는 방법 |
| --- | --- | --- | --- |
| `prism-parts` · `cylinder-parts` | 밑면 두 개, 높이 | **됨** | 돌려 봐도 어느 면이 밑면인지 화면이 알려 주지 않는다(면 색·표시가 모두 같음). 면을 누르는 것과 끄는 것은 8px로 가른다 |
| `prism-judge` · `cylinder-judge` | 돼요 / 안 돼요 | 안 됨 (지금과 같음) | 펼친 전개도는 늘 위에서 본 처음 모습. 접기 막대·조작판 잠금(spec 17-16) |
| `prism-edge` | 선분 | 안 됨 | 맞히기 전에는 접히지 않는다. 힌트(반만 접기) 동안에도 잠금 |
| `cylinder-size` | 카드 · 길이 | 안 됨 | 카드를 붙이기 전에는 말리지 않는다. [굴려 재기]는 한 번 틀린 뒤의 힌트 |
| `prism-free` · `cylinder-free` | 예상 | 무대가 없다(놓는 판) | spec 16-1과 같음 |
| `blocks-where` | 화살표 | **안 됨** | 돌리면 그 모습이 보이는 방향을 찾을 수 있다. 판은 처음 보기로 멈춰 있고 방향 버튼·조작판이 없다 |
| `blocks-scene` · `blocks-numviews` · `blocks-layer-views` | 모습 · 그림 · 개수 | **입체가 없다** | 답하기 전에는 2D 자료(배치 그림, 수, 층별 모양)만 있다. 입체는 답한 뒤에 만들어진다 |
| `blocks-count` | 개수 | **안 됨** | 숨겨진 쌓기나무가 과제다. 답하기 전에는 **보이는 면만 있는 멈춘 그림**(숨겨진 쌓기나무는 DOM에도 없다). 층별로 벌려 보기는 답한 뒤 |
| `blocks-flip` · `blocks-draw` | 반대쪽 모습 · 그 방향의 그림 | **안 됨** | 멈춘 그림. `blocks-draw`는 숨겨진 쌓기나무가 없는 모양만 내고 개수도 알려 준다(교과서 72쪽 확인 문제와 같은 방식) |
| `blocks-copy` · `blocks-hidden` · `blocks-build` · `blocks-fromnum` · `blocks-layer-build` | 내가 만든 모양 | 내 판은 **됨**, 주어진 그림은 안 됨 | 답은 내가 만든 것이라 돌려 봐도 드러날 것이 없다. [앞]을 눌러 내 쌓기를 앞에서 보고 그림과 견주는 것은 실물로 할 때와 같은 학습 행동이다. **내 쌓기의 2D 그림을 자동으로 그려 주지는 않는다**([확인하기]를 눌러야 견줌) — 그림끼리 맞추는 놀이가 되지 않게. 주어진 그림에는 보이는 면만 있다 |
| `blocks-write` · `blocks-layer-draw` | 수 · 층 모양 | **됨** | 돌려 보며 적는 것이 과제다(실물 쌓기나무를 보고 적는 것과 같다). 바로 위에서 보면 자리만 보이고 높이는 안 보인다. "쌓기나무를 누르면 수가 뜨는" 기능과 층마다 다른 색은 답한 뒤에만 |
| `blocks-add` | 만들 수 있는 모양 | 보기는 멈춘 그림, 내 판은 예상한 뒤에 열림 | 직접 붙여 보는 것은 예상을 기록한 뒤의 확인이다 |

- 멈춘 그림과 잠근 무대의 모습은 문항과 무관해야 한다(방향·크기·버튼 상태가 한 가지). 지금 전개도 무대의 검사("답하기 전 36화면이 한 가지 모습")를 쌓기나무에도 쓴다.
- 화면 읽기 알림은 방향·개수 변화만 말한다("앞에서 본 모습이에요", "2줄 3칸에 쌓았어요. 모두 7개"). 멈춘 그림 단계에서는 자리별 높이를 읽어 주지 않는다.
- 테스트가 정답을 아는 방법은 지금과 같다: 같은 시드로 `logic`을 불러 계산한다(DOM에 정답을 숨겨 두지 않는다).

## 6. 기술 설계

### 6-1. 3D 표현 다시 견주기 (용량 한도가 없어진 뒤 — 시제품으로 잼)

같은 쌓기나무 장면을 네 방식으로 그리고, 화면의 표본 점마다 "광선 계산으로 구한 맨 앞 면"과 견줬다(Chromium, 무대 806×440, 보기 24가지 × 장면 6가지, 장면마다 표본 약 15만 점). 돌리는 동안의 프레임 간격은 CPU를 1·4·6배 느리게 해서 쟀다. 판을 3×3칸·3층으로 줄이기 전에 잰 값이라 장면이 지금 계획보다 크다(작아진 쪽이므로 결론은 그대로다).

| 기준 | (가) CSS 3D (지금 무대 방식) | (다) 직접 투영 + SVG | 직접 투영 + Canvas | (나) WebGL |
| --- | --- | --- | --- | --- |
| 깊이 순서 오류 (화면 색) | **0** (모든 장면) | **0** | **0** | **0** |

**결정 (Plan이 정함. 교과서를 읽은 뒤에도 그대로)**

| 영역 | 방식 | 까닭 |
| --- | --- | --- |
| 쌓기나무 | **(다) 직접 투영 + SVG** — 새 파일 `block-view.js` | 깊이 순서를 순수 함수로 직접 정하므로(격자 칸은 축마다 눈에서 먼 것부터 그리면 늘 맞다) Node 단위 테스트로 검사되고, 브라우저의 3D 정렬에 기대지 않는다. 면이 `<polygon>`이라 누르기 판정과 e2e가 정확하다. 평행 투영([위][앞][옆]이 2D 그림과 똑같이 보임)도 식 하나다. **교과서식 멈춘 그림도 같은 함수로 그린다.** 느려지지 않는다(위 표) |
| 각기둥 · 원기둥 | **(가) CSS 3D** — 지금 `view3d.js`를 넓힘 | 접는 장면·표시·돌려 보기·e2e가 이미 있고, 면이 8개 안팎(원기둥은 38개)이라 문제가 없다. 사용자가 좋다고 한 화면 그대로다 |
| 정육면체 · 직육면체 | 그대로 CSS 3D | 옮길 까닭이 없다 |
| WebGL · Three.js | **쓰지 않는다** | 이 크기의 장면에서 더 나은 것이 없고(위 표), 누르기·접근성·글자·테스트를 모두 따로 만들어야 하며, 지금 화면과 어울리게 하려면 일이 더 든다. 나중에 꼭 필요한 장면이 생기면 영역별로 늦게 불러오는 구조(7절)라 그 영역에만 넣을 수 있다 |

- CSS 3D에서 **입체 상태의 면을 누르는 단계**(`prism-parts`·`cylinder-parts`)는 브라우저 판정 대신 직접 계산한 판정을 쓴다(`pickFace`: 화면 점에서 맨 앞 면. 거의 옆으로 선 면은 누를 수 없는 면으로). 위 표의 어긋남이 면 6~8개짜리 입체에서 얼마나 드문지는 재지 않았지만, 계산이 15줄이라 피하는 쪽이 싸다. 원기둥의 옆면(띠 36개)은 띠 하나를 누르면 옆면 전체가 눌린 것으로 본다.
- **원기둥 곡면(시제품)**: 띠 24 · 36 · 48개 모두 6배 느린 CPU에서 프레임 간격 16.7ms(34ms 넘음 0), 그리는 JS 0.1~0.8ms. 눈으로 본 결과: 띠 24개는 띠 경계가 보이고 **36개부터 매끈**하다. 띠를 딱 맞게 놓으면 띠 사이에 바탕색 실금이 보여 **0.6px씩 겹쳐 놓아야** 한다. 밑면 원은 `border-radius: 50%`로 충분하지만 키웠을 때 가장자리가 거칠어 지금 무대의 "선명하게 그리는 배수"(`raster`)를 그대로 써야 한다. 옆 윤곽선(잉크 선)은 띠 테두리로는 생기지 않는다 → 보는 방향과 수직인 두 띠에만 테두리를 준다(Build에서 만들어 확인).

### 6-2. 데이터 모델 (모두 순수 데이터)

```js
// 각기둥: 입체에서 시작한다 (spec 11-2의 unfold를 2차에서 만들고 여기서 넓힘)
prismSolid({ base: [[x, y], ...], height })      // 밑면 볼록 다각형(cm) + 높이 → 면·모서리·이면각이 있는 입체
unfold(solid, tree)                              // 면 이웃 그래프의 신장 트리 → 전개도 { kind: 'prism', faces: [{ id, role: 'base'|'side', label, poly }], root }
// 원기둥: 판정은 해석적으로, 그릴 때만 띠로
{ kind: 'cylinder', side: { w: 12.4, h: 5, shape: 'rect' },    // 옆면: 놓인 가로·세로(cm). shape: 'rect' | 'trapezoid'(안 되는 보기)
  circles: [{ r: 2, edge: 'top', at: 6.2 }, { r: 2, edge: 'bottom', at: 3 }],   // 원이 붙은 변과 그 변 위의 자리
  pi: 3.1 }                                                    // 이 문항이 쓰는 원주율 값 (13절 1번)
toStrips(net, 36)                                // 그리기용: 띠 36개 + 원 2개 (띠 사이 이면각 360° / 36)
// 쌓기나무: 높이 지도 (뜬 것 없음)
{ cols: 3, rows: 3, max: 3, h: [[2, 1, 0], [1, 1, 1], [0, 0, 0]] }   // h[줄][칸] = 그 자리에 쌓인 개수. 줄 0 = 앞줄, 칸 0 = 왼쪽(앞에서 볼 때)
// 1차시 조형물: 높이 지도 + 자리마다 색
{ ...높이 지도, color: [['yellow', null, null], [null, 'blue', null], [null, null, 'red']] }
```

- 각기둥의 경첩 각도는 **입체의 이면각**에서 온다: 옆면-옆면 = 밑면의 그 꼭짓점의 바깥각(정다각형이면 360° ÷ 변의 수), 밑면-옆면 = 90°. 밑면이 정다각형이 아니어도 같은 식이다.
- 원기둥 모델은 spec 11-2에서 조금 넓혔다: 원이 붙는 변을 위·아래뿐 아니라 왼쪽·오른쪽도 받고(세워 놓은 꼴), 두 원의 자리(`at`)가 달라도 되며(엇갈린 자리), 옆면 모양에 사다리꼴을 둔다 — 모두 교과서 125쪽 보기의 종류다.
- 쌓기나무를 "칸의 집합"이 아니라 높이 지도로 두는 까닭: 뜬 것이 없으면(15절 3번, 교과서도 같은 전제) 둘은 같고, 높이 지도는 그대로 "위에서 본 모양에 수 쓰기"(4차시)이며, 층별 모양(5차시)은 "높이가 k 이상인 자리"다. 되돌리기·견주기·문제 만들기가 단순해진다.

**쌓기나무 — 새 파일 `blocks.js`** (h = 높이 지도)

| 함수 | 내용 | 쓰는 단계 |
| --- | --- | --- |
| `count(h)` · `cellsOf(h)` | 개수, 칸 목록 `[x, y, z]` | 모두 |
| `topView(h)` · `frontView(h)` · `sideView(h)` | 위: 쌓인 자리(바닥에 닿은 면) / 앞: 세로줄(왼쪽 → 오른쪽)마다 가장 높은 층 / 옆(= 오른쪽에서): 줄(앞 → 뒤)마다 가장 높은 층 | 3~5차시 |
| `backView(h)` · `leftView(h)` · `flipLR(view)` | 뒤·왼쪽에서 본 모양 = 앞·옆에서 본 모양을 좌우로 뒤집은 것 | `blocks-flip` |
| `sceneFrom(h, color, dir)` | 조형물이 놓인 판을 둘레 네 방향에서 본 모습: 세로줄·층마다 가장 가까운 것의 색 | 1차시 |
| `layerOf(h, k)` · `fromLayers(layers)` | k층 모양(높이가 k 이상인 자리) / 층별 모양 → 높이 지도(아래층에 없는 자리에 위층이 있으면 오류) | 5차시 |
| `fitsViews(h, { top, front, side })` · `diffViews(h, target)` | 세 그림에 맞는지, 다른 칸 목록(피드백용) | `blocks-build` |
| `maxFill({ top, front, side })` · `minCount(…)` | 세 그림에 맞는 가장 많은 쌓기(자리마다 `min(앞, 옆)`)와 가장 적은 개수 → 하나로 정해지는가 | `blocks-build`, 문제 만들기 |
| `pictureKey(h)` · `sameLook(a, b)` | 교과서 방향의 멈춘 그림에서 보이는 조각들(자리와 면 방향). 두 쌓기가 **같아 보이는가**. 판 위에서 통째로 옮긴 것은 같다고 본다 | `blocks-copy`, `blocks-hidden` |
| `lookAlikes(h, { top })` · `hiddenCells(h)` | 그림(과 위에서 본 모양)이 같은 쌓기 전부 / 그 그림에서 한 면도 보이지 않는 쌓기나무 | `blocks-count`, `blocks-hidden`, 문제 만들기 |
| `addOne(h)` · `madeFrom(base, shape, n)` | 한 개 더 붙인 모든 모양 / `shape`가 `base`에 n개를 더 붙여 되는가(놓인 방향 그대로) | 도전 `blocks-add` |
| `place(h, target)` · `remove(h, target)` · `targetOf(hit, mode)` | 누른 곳(바닥 자리·윗면·옆면) → 바뀌는 자리. 3층·판 밖 판정 | 쌓는 단계 |
| `paintOrder(cells, viewDir)` · `visibleFaces(cells, viewDir)` | 그리는 순서(축마다 눈에서 먼 칸부터)와 보이는 면 — `block-view.js`가 쓴다 | 무대·그림 |
| `judgeDirection` · `judgeLook` · `judgeCount` · `judgeDrawing` · `judgeBuild` · `judgeNumbers` · `judgeLayers` · `judgeAdd` | 단계별 채점 → `{ correct, tag, diff }` | — |

- **"같아 보이는가"의 계산**: 멈춘 그림은 교과서처럼 원근 없이, 앞·오른쪽·위가 같은 비율로 보이는 방향에서 그린다. 그 방향에서는 보이는 세 면이 저마다 삼각 조각 둘로 나뉘고, 조각 하나는 다 보이거나 다 가려지거나 둘 중 하나다. 그래서 그림은 "조각의 자리 + 면 방향" 목록으로 정확히 적히고, 두 쌓기의 목록이 같으면 같은 그림이다(scratchpad 시제품 `lookalike.mjs`로 3×3칸·3층의 높이 지도 262,144개를 모두 계산함 — 12초).

### 6-4. 문제 만들기 (시드 `ctx.rng`로 재현)

| 영역 | 만드는 방법 | 만들 때 스스로 검사 |
| --- | --- | --- |
| 각기둥 판별 | 입체(밑면 종류 · 변 2~5 cm · 높이 3~7 cm) → 신장 트리로 펼침. 띠 꼴 = 옆면이 한 줄, 낯선 꼴 = 옆면 하나가 밑면에 붙은 꼴. 안 되는 것 = 옆면 하나 빼기·더하기 / 밑면을 같은 쪽으로 옮기기 / 옆면 하나의 가로 바꾸기 / 옆면 하나를 평행사변형으로 | `checkNet`이 의도한 문제 종류를 내는지(spec 11-4와 같은 원칙), 무대에 들어오는 크기인지 |
| 각기둥 맞닿는 선분 | 되는 전개도에서 경첩이 아닌 변 하나를 고르고 `matchingEdge`로 짝을 찾음. 오답 보기에 바로 옆 선분과 길이가 같은 다른 선분 | 짝이 하나뿐인지 |
| 각기둥 완성하기 | 입체 하나 + 미리 놓을 면(첫 과제: 밑면 1 + 옆면 1~2, 둘째 과제: 밑면 1) | 남은 카드로 완성하는 방법이 2가지 이상인지 |
| 원기둥 | 밑면의 반지름 1~3 cm(0.5 단위), 높이 2~6 cm, `pi`. 되는 꼴: 흔히 보는 꼴 / 세워 놓은 꼴 / 원이 엇갈린 자리. 안 되는 것: 두 원을 같은 변으로 / 한 원의 반지름 바꾸기 / 옆면을 사다리꼴로. 카드: 가로가 둘레 · 지름 · 반 바퀴 | `checkCylinder`가 의도한 문제 종류를 내는지, 카드 셋의 길이가 서로 다른지, 답이 그 `pi` 값에서 소수 둘째 자리 안에서 떨어지는지 |
| 쌓기나무 | 3×3칸 안에서 이어진 바닥 모양(3~7자리)에 자리마다 높이 1~3을 줌. 개수 5~12. 조건에 맞을 때까지 다시 뽑는다 | 아래 표의 단계별 조건 |

쌓기나무의 단계별 조건과 그런 모양이 얼마나 있는지 (시제품 `lookalike.mjs`: 3×3칸·3층의 높이 지도 262,144개 가운데 바닥이 이어지고 5~12개인 **56,478개**를 모두 셈)

| 조건 | 쓰는 단계 | 해당하는 모양 |
| --- | --- | --- |
| 그림에서 숨겨진 쌓기나무가 없음 | `blocks-draw`, `blocks-flip`, `blocks-count`의 절반 | 4,774개 (8.5%) |
| 그림만으로는 개수가 정해지지 않음 | `blocks-copy`의 둘째 문항 | 46,283개 (81.9%) |
| 그림 + 위에서 본 모양으로 쌓기가 하나로 정해짐 | `blocks-count`, `blocks-hidden`의 "하나뿐" 문항 | 39,041개 (69.1%) |
| 그림 + 위에서 본 모양이 같아도 개수가 여러 가지 | `blocks-hidden`의 "여러 가지" 문항 | 17,437개 (30.9%) — 될 수 있는 개수가 2가지인 것 14,662 · 3가지 2,337 · 4가지 이상 438 |
| 위·앞·옆으로 쌓기가 하나로 정해짐 | `blocks-build`의 앞 2문항 | 12,636개 (22.4%) |
| 위·앞·옆이 같아도 개수가 여러 가지 | `blocks-build`의 끝 문항 | 43,842개 (77.6%) |

- 어느 조건이든 수천 개가 있어 몇 번 안에 뽑힌다. "자리마다 `min(앞, 옆)`으로 채운 쌓기 = 세 그림에 맞는 가장 많은 쌓기"는 같은 시제품에서 24,552묶음 모두 맞았다(독립 검사). 시제품은 "조각 하나는 다 보이거나 다 가려진다"도 스스로 검사했다(조각 안의 무작위 점 넷씩, 어긋남 0). 표의 수는 판 위의 자리까지 같은 쌓기끼리 센 것이다(앱의 `sameLook`은 통째로 옮긴 것도 같다고 보므로 `blocks-copy`에서는 같아 보이는 쌓기가 조금 더 많다 — 판 가장자리에 걸친 경우에 개수가 정해지는지가 달라질 수 있는지는 재지 않았고, S1의 단위 테스트에서 전부 나열해 확인한다).
- `blocks-where`·`blocks-scene`: 조형물 셋의 자리·색·높이를 뽑고, 둘레 네 방향의 모습이 모두 다른 배치만 쓴다. `blocks-add`: 3~5개짜리 모양 + `addOne`의 결과에서 되는 보기 2개, 안 되는 보기 1~2개(두 개를 붙여야 하는 모양, 하나를 옮겨야 하는 모양).

(3) Three.js를 넣으면 gzip 139 KB가 더해져 느린 망에서 0.7초쯤 더 걸린다(계산값) — 넣는다면 반드시 늦게 불러와야 한다.

### 15-2. 직접 만드는 단계에는 예상하기가 없다 (2026-10-10 사용자 결정, [spec.md](spec.md) 16-12)

사용자가 "내 맘대로 전개도"의 접기 전 예상하기를 없애기로 했다(스스로 만든 전개도에 "안 될 거예요"를 고르는 것이 어색함). **이 문서의 직접 만드는 단계(`prism-free`, `cylinder-free`)도 같은 원칙을 따른다**: 예상 버튼 없이 [접어 보기] 하나로 접고, 별은 찾은(완성한) 가지 수로 정하며, 안 되는 모양을 접어도 별이 깎이지 않는다. 본문에 "예상하고 접기"로 적힌 곳은 이 절이 바꾼다. 주어진 그림을 보고 답하는 판별 단계(`prism-judge`, `cylinder-judge`)와 쌓기나무의 예상 물음은 그대로다.

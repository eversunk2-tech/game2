# Build 서브에이전트 지침: B0c2 인트로 그림 선명하게 · 꽉 채우기와 카드형 · 큰 그림은 따로 파일로 (트랙 "b0")

## 역할

너는 게임 인트로(B0c)를 만든 **Build** 담당이다. 사용자의 새 요청([spec-grade6.md](spec-grade6.md) **15-9**)을 반영한다. 검증은 별도 Review 서브에이전트가 한다(B0c와 이번 일을 함께 본다).

사용자의 말: "인트로 화면 해상도가 낮아서 선명도가 떨어지겠지? 내가 캔바에서 2880픽셀 해상도로 업스케일링 해서 다운받을 테니깐 … 그리고 화면 꽉차거나 카드형으로 하는 규칙은 지금 selectio-game 프로젝트에서 정한 것과 같은 방식으로 해줘" · "파일 크기는 1mb로 내가 저장할게"

## 할 일

### 1. 새 그림으로 바꾸기 — 바이트 그대로

- 사용자가 캔바 AI 업스케일로 내려받은 두 파일(배경 JPG, 투명 바탕 제목 PNG — 각각 약 1 MB, 폭 2880 안팎)이 `src/games/net-workshop/img/`에 있다(코디네이터가 이름을 `intro-bg.jpg`·`intro-title.png`로 맞춰 커밋해 준다 — 프롬프트에서 알려 준다).
- **받은 파일을 바이트 그대로 쓴다**: 다시 저장·자르기·크기 바꾸기·형식 바꾸기(WebP 등) 금지. 까닭: 캔바 AI 그림의 출처 정보(C2PA)를 지우거나 바꾸는 것을 캔바 AI 약관이 금한다(selectio game에서 확인 — 15-9절). 빌드 결과물의 그림 파일도 원본과 **md5가 같아야** 한다(검사로 고정).
- 옛 `img/intro-title.webp`(코디네이터가 잘라 WebP로 바꿔 출처 정보가 빠진 것)는 지운다. 옛 1680 `intro-bg.jpg`는 새 파일로 바뀐다.
- 그림의 실제 크기·투명 바탕 여부를 직접 재서 보고하고, 제목 그림의 빈 둘레(투명 여백)가 크면 **CSS로** 그 안의 글자 상자만 쓰도록 맞춘다(파일은 그대로).

### 2. 큰 그림은 따로 파일로 (빌드 — B0b의 일부를 앞당김)

- 지금 빌드는 CSS `url()`의 그림을 HTML 안에 `data:`로 넣는다. 2880 그림 두 장(약 2 MB)을 넣으면 게임 파일이 약 3 MB가 되고 느린 망에서 첫 화면이 비어 있는 시간이 길어진다(B0c Review 전 잰 값: 1680 그림으로도 1.1 → 3.0초).
- **큰 그림(예: 게임 폴더 `img/` 아래의 사진·그림 파일, 또는 크기 기준을 정해)은 `dist/assets/이름-해시.확장자`로 따로 내보내고 HTML·CSS에서는 상대 주소(`./assets/…`)로 가리키게** 한다. 작은 그림(SVG 아이콘·표지 등)은 지금처럼 `data:`로 둔다(정한 기준을 보고). esbuild의 `file` 로더 등 — 파일을 다시 인코딩하지 않는 방법으로(바이트 그대로).
- 빌드의 검사를 넓힌다: ① 바깥 주소 없음은 그대로(상대 주소 `./assets/`만 허용, `/`로 시작하는 주소 금지 — 사이트가 `/game2/` 하위 경로라서) ② 가리키는 파일이 모두 있음 ③ 빌드 로그에 게임마다 "HTML 크기 + 따로 나간 그림 크기". 게임 모음(`dist/index.html`)과 예시 게임은 결과가 지금과 같아야 한다(따로 나갈 그림이 없으면 한 글자도 같게).
- 브라우저 검사는 지금처럼 `file://`로 `dist/`를 연다 — 상대 주소 그림이 열리는지 확인. GitHub Pages(`dist/` 전체를 올림)에서도 그대로 열리는 구조인지(하위 경로 `/game2/`를 흉내 내는 작은 서버로 한 번 직접 열어 확인 — 저장소에 서버를 더하지는 않는다, scratchpad에서).
- `scripts/build.mjs`·`scripts/lib/**`·`tests/unit/build.test.js`·`docs/dev-guide.md`·`docs/engine.md` 7절(그림 넣기)·`README.md`의 해당 문장을 사실에 맞게.
- 그림이 받아지기 전에는 B0c에서 만든 하늘색 바탕이 먼저 보이고 받아지면 부드럽게 바뀌는지(빈 화면 0), 느린 망(1.6 Mbps·지연 150ms)에서 첫 화면 시간을 다시 잰다.

### 3. 꽉 채우기와 카드형 — selectio game과 같은 규칙 (15-9절)

1. **꽉 채우기**: 화면을 덮도록 배경 그림을 놓되 **1.35배까지만 늘린다**(그림 CSS 폭 × `devicePixelRatio` ÷ 그림 폭 ≤ 1.35, 상수 이름 예: `INTRO_UPSCALE_MAX`).
2. **꼭 보일 칸은 자르지 않는다 — 인물을 자르지 않는다**: 새 배경 그림에서 두 아이(왼쪽 소년·오른쪽 소녀 — 얼굴과 몸, 들고 있는 전개도까지)의 자리를 그림 좌표로 재서(보고) 꽉 채울 때 그 칸이 화면 밖으로 나가면 꽉 채우지 않는다. 제목·[입장하기] 자리도 지킨다.
3. 그렇게 해도 남는 띠(위아래 합 ÷ 화면 높이, 양옆 합 ÷ 화면 폭 가운데 큰 값)가 **5%를 넘으면 "얇은 여백 카드"**(상수 예: `INTRO_BAND_MAX = 0.05`): 그림 전체가 보이는 둥근 모서리(약 18px) 카드, 흰 테 2px + 그림 색의 은은한 빛 + 아래 그림자, 뒤는 같은 그림을 흐리게(작은 캔버스나 CSS `filter: blur` — 새 파일을 만들지 않는다), 여백은 양옆·위 12px, 아래는 [입장하기]가 카드 아래 가장자리에 걸칠 자리만. **카드는 늘리지 않는다**(1.0 — 그림 폭 = `min(그림 폭 ÷ DPR, 화면 폭 − 24, (화면 높이 − 12 − 아래 자리) × 그림 비율)`). 금테 액자는 만들지 않는다.
4. 화면 크기·방향·`devicePixelRatio`가 바뀌면 모드를 다시 정한다. 제목·부제·버튼·별·떠오르는 입체는 두 모드 모두에서 그림에 맞춰 놓인다(카드 모드에서는 카드 안에).
5. **기기별 결과표**를 실제 함수로 만들어 보고한다: 1366×768·DPR 1, 1366×680·DPR 1, 820×1180·DPR 2, 390×844·DPR 3, 1024×768·DPR 2(4:3 iPad), 1180×820·DPR 2, 1280×800·DPR 1.5·2, 1366×1024·DPR 2(iPad Pro), 1920×1080·DPR 1·2, 844×390·DPR 3 — 각 모드(꽉 채우기/카드), 늘림 배율, 띠 %, 인물 칸이 다 보이는지.
6. 움직임 줄이기·`?fx=low`·접근성·[입장하기] 길은 B0c 그대로.

### 4. 합친 상태에서 검사 손질 (B0c에서 하다 만 일)

- 이 가지에는 직육면체 M3가 합쳐져 있다(`40b076b` — M3은 재검토 통과, 그 뒤 `track/cuboid`에 review 파일 커밋 하나가 더 있다 — 코디네이터가 합쳐 준다). 합친 상태에서 인트로 때문에 깨지는 직육면체 검사(예: `tests/e2e/net-workshop-cuboid-box.spec.js` 735·1097행)를 앱을 연 뒤 [입장하기]를 누르게 고친다 — 들어가는 길만.

## 반드시 지킬 것

- [common-rules.md](common-rules.md) 전부. 인트로 배치 검사는 움직임 줄이기로 연 화면에서, 다섯 크기 + 위 결과표의 크기들(DPR은 Playwright의 `deviceScaleFactor`로)에서 스크롤 0·잘림 0·겹침 0·인물 칸이 다 보임·부제가 리본 안.
- 그 밖의 화면·예시 게임·게임 모음은 B0c 때와 같다(불변 수치). 저장 열쇠·값 그대로.
- 브라우저 검사는 느린 기기를 견디게(움직임이 끝난 뒤, 사라지는 알림은 조작 바로 뒤, 머무는 시간, 시간 예산), `waitForTimeout`·`retries` 금지. 끝내기 전에 CPU 느리게 하기 4·8·12배로 새로 만들거나 고친 검사 값 실패 0.
- 테스트: `npm test`, `npm run test:e2e -- --workers=4`, `E2E_WIDE_TEXT=font npm run test:e2e -- --workers=4` 모두 실패 0(합친 상태에서).

# Plan 서브에이전트 지침: 전개도 접기 공방

## 역할과 범위

- 너는 **Plan** 단계 담당이다. 게임 계획서 `docs/games/net-workshop/spec.md` **한 파일만** 새로 쓴다.
- 저장소의 다른 파일은 **읽기만** 한다. `src/`, `scripts/`, `tests/`, `package.json` 등을 고치지 않는다. 구현 코드를 쓰지 않는다.
- `git commit`, `git push`, `npm install`(저장소 안)을 하지 않는다.
- 크기 확인·짧은 실험이 필요하면 저장소 밖 `/tmp/claude-0/-home-user-game2/51527575-3484-5179-b863-3acfe59f4ca9/scratchpad/plan/`에서만 한다.
- 막히는 점(자료 접근 불가 등)은 spec.md의 "사용자에게 확인할 것"에 적고, 추측으로 채우지 않는다.

## spec.md에 반드시 담을 내용

`docs/game-design-template.md`의 1~10절을 모두 채우고, 아래 11~15절을 덧붙인다. 한국어로 쓴다.

1. **교육과정 연결** — 학년·학기·단원별로 이 게임이 다루는 입체와 활동. 초등에서 전개도를 실제로 다루는 입체가 무엇인지 구분한다(예: 구는 전개도가 없음, 원뿔 전개도를 초등에서 다루는지). **성취기준 코드·원문은 출처에서 확인한 것만** 쓰고, 확인 못 하면 "확인 필요"와 이유를 적는다. (참고: 이 환경에서 goe.go.kr PDF는 403으로 막혀 있었다. 웹 검색으로 확인되면 출처 URL을 함께 적는다.)
2. **차시별 구성** — 차시(10분 안팎) 단위 묶음을 정하고, 묶음마다 단계(stage) 목록, 끝나는 조건, 별 기준을 표로. 선생님이 해당 차시 묶음으로 바로 들어가는 방법(예: 주소 옵션)도 정한다. 지금 엔진은 단계가 한 줄로 이어지고 앞 단계를 마쳐야 열린다 — 차시별 구성에 맞추려면 엔진에 무엇을 바꿔야 하는지(또는 바꾸지 않는 방법) 최소 변경으로 제안한다.
3. **개인/모둠** — 백엔드 없이 가능한 모둠 방식이 있는지 검토한다(예: 한 기기로 돌아가며 하기, 교실 TV 시범). 서버·네트워크 통신은 쓰지 않는다. 추천안을 쓰되 사용자가 고를 수 있게 "사용자에게 확인할 것"에 올린다.
4. **오개념 표** — 전개도에서 학생이 자주 막히는 지점(겹치는 면, 마주 보는 면, 맞닿는 모서리 길이, 각기둥 옆면 수와 밑면의 관계, 원기둥 옆면의 가로 길이와 밑면 둘레 등)을 tag 이름까지 정한다. tag는 학습 기록에 그대로 남는 짧은 한국어.
5. **핵심 놀이** — 학생이 화면에서 하는 행동(예: 전개도 접기 애니메이션 보며 판별, 면을 붙여 전개도 완성, 마주 보는 면 찾기 등)과 그 행동이 연습하는 개념. 마우스·터치·키보드로 모두 할 수 있어야 하고 1366×768에서 스크롤 없이 플레이돼야 한다.
6. **피드백** — 틀렸을 때 "왜" 틀렸는지 보여 주는 방법(예: 접히는 장면에서 겹치는 면 강조).

### 11. 기술 설계

- **3D 표현 방식 비교 후 추천**: (a) CSS 3D transform으로 면을 경첩처럼 접기, (b) Three.js를 npm으로 넣고 esbuild로 묶기(CDN 금지), (c) Canvas 2D에 직접 투영. 기준: HTML 한 파일 크기, 저사양 크롬북 성능, 터치·키보드 조작, 구현량, 원기둥(곡면) 표현 가능 여부. Three.js라면 묶은 뒤 예상 크기를 적는다(`npm view three` 정보나 scratchpad 실험으로).
- **전개도 데이터 모델**: 정육면체(격자 칸), 직육면체(크기가 다른 직사각형), 각기둥·각뿔(다각형 면 + 모서리 연결), 원기둥(원 2개 + 직사각형) 각각을 어떻게 표현할지.
- **접힘 판정 알고리즘**: 전개도가 입체로 접히는지(면 겹침, 빠진 면, 맞닿는 모서리 길이 불일치) 판정하는 순수 함수 설계. 예: 경첩 트리를 따라 각 면의 접힌 뒤 위치를 계산해 겹침 검사. 정육면체 전개도 11가지와 같은 알려진 사실로 검증할 수 있게 쓴다. 이 함수들은 `logic.js` 계열 순수 함수로 Node에서 단위 테스트한다.
- 문제 생성(무작위 전개도, 틀린 전개도 만들기)이 필요하면 방법.

### 12. 파일 구조

- `src/games/net-workshop/` 아래 파일과 각 파일의 역할.
- 공통 엔진(`src/shared/`) 변경이 필요하면 무엇을, 왜 바꾸는지와 다른 게임에 주는 영향.
- 추가 npm 의존성이 있으면 이름·버전·이유.

### 13. 테스트 계획

- 단위 테스트(`tests/unit/net-workshop*.test.js`): 무엇을 검사하는지 목록.
- 브라우저 테스트(`tests/e2e/net-workshop.spec.js`): 크롬북·태블릿에서 확인할 흐름.

### 14. Build 단계 나누기

- 한 번에 다 만들기 어렵다면 마일스톤으로 나눈다(예: 1차 = 정육면체 차시 하나로 끝까지 동작). 마일스톤마다 "끝났다"의 기준.

### 15. 사용자에게 확인할 것

- 사용자가 정해야 하는 것만, 선택지와 추천을 붙여 짧게(5개 이하).

## 분량과 형식

- 읽기 쉬운 표·목록 위주. 400줄 안팎을 넘지 않게.
- 맨 위에 3~5줄 요약(무엇을 만드는지, 차시 구성, 3D 방식, 개인/모둠 결론).

# Review 서브에이전트 지침: S1 쌓기나무 — 느린 기기에서 흔들리는 검사 확인 (트랙 "blocks")

## 역할과 범위

- 너는 **Review** 담당이다. Build가 [build-fix-brief-s1c.md](build-fix-brief-s1c.md)에 따라 고친 **검사 파일 하나**를 **독립적으로** 확인한다. Build와 분리된 검토자다. 앱 코드는 지난 재검토(`962e5fc`, 통과)에서 달라지지 않았어야 한다.
- 트랙의 작업 폴더 안 `docs/games/net-workshop/review-blocks.md` **한 파일만** 고친다: 맨 아래에 `## 재검토 2 (S1c 흔들리는 검사 확인)` 절을 덧붙이고, 맨 위 "판정"·"검토일" 줄을 고친다. 앞 내용은 지우지 않는다. 커밋하지 않는다.
- 코드·테스트·다른 문서를 고치지 않는다. 커밋·브랜치 바꾸기·작업 트리를 바꾸는 git 명령 금지(읽기용은 된다). `npm install`·`npm ci`·내려받기 금지.
- **트랙의 작업 폴더에서만** 일한다(코디네이터가 프롬프트로 알려 준다). 검증 파일·복사본은 정해 준 scratchpad 폴더에만. Build의 scratchpad는 근거로 삼지 않는다.

## 검토 대상

`962e5fc`(지난 재검토 대상)와 트랙 브랜치의 마지막 커밋 사이의 변경 전부(`f440d9b`는 코디네이터가 review-blocks.md만 커밋한 것). **`tests/e2e/net-workshop-blocks.spec.js` 말고 다른 파일이 바뀌었으면 범위 위반**이다(`src/**`가 한 줄이라도 바뀌었으면 지난 재검토의 통과가 그대로라고 볼 수 없다). Build의 최종 보고는 코디네이터가 요약해 전한다 — **확인 대상이지 근거가 아니다.**

## 확인할 것

1. **범위**: `git diff 962e5fc..HEAD --stat`. 저장소의 검사 파일에 재현용 코드(CPU 느리게 하기)가 남지 않았는지.
2. **원인**: "정답 노출 0 (이쪽에서 보면?) …" 검사가 재는 순간과 고른 보기의 `pop` 움직임(0.35초, 최대 `scale(1.08)`)이 겹친다는 설명이 맞는지 직접 잰다(답한 뒤 시간별 보기 그림 폭).
3. **느린 기기 흉내 (가장 중요)**: scratchpad에 푼 복사본의 검사 파일 맨 위에 CPU 느리게 하기(`Emulation.setCPUThrottlingRate`)를 넣어 —
   - **`962e5fc` 복사본**: `SLOW_CPU` 0·4·8·12로 `net-workshop-blocks.spec.js` 전체를 돌려 느린 기기에서만 실패하는 검사 목록을 직접 만든다(시간 제한만 넘긴 것은 따로 표시).
   - **지금 것의 복사본**: 같은 배수에서 그 목록이 0인지(두 기기 모두). 고친 검사들은 `--repeat-each=8` 이상.
   - Build의 목록과 견줘 놓친 것이 있는지. 시간 제한만 넘기는 검사는 느리게 하기 실행에서만 `--timeout`을 늘려 다시 돌려 뜻이 통과인지 본다.
4. **검사의 뜻이 그대로인지**: `git diff 962e5fc..HEAD -- tests/`를 줄마다 읽는다 — 넣은 것이 "움직임이 끝날 때까지 기다리기"뿐인지, 기대값(`toBe`·`toEqual`·문턱)·재는 항목·장면 수가 줄거나 느슨해지지 않았는지, `waitForTimeout`·허용 오차·`retries`로 덮지 않았는지. 기다림이 끝나지 않을 길(끝없이 도는 애니메이션, 움직임 줄이기 설정)이 없는지. 고친 검사가 여전히 앱의 회귀를 잡는지 — 복사본의 앱 코드·스타일을 일부러 망가뜨려(예: 답한 뒤 보기 넷 가운데 하나만 크게, 답하기 전에 입체를 보이게) 그 검사가 실패하는지 2~3가지로 본다.
5. **놓친 곳**: 답하기·누르기·포인터 올리기 직후에 크기·자리·겹침·넘침을 재는 곳을 검사 파일 전체에서 훑어, Build가 "같은 문제가 아니다"라고 본 판단이 맞는지(표본으로 직접 재서).
6. **테스트**: `npm test`, `npm run test:e2e -- --workers=4`, `E2E_WIDE_TEXT=font npm run test:e2e -- --workers=4`를 직접 실행(통과·실패·건너뜀). `tests/e2e/engine-features.spec.js`의 "플레이 머리 높이 …"가 `시간 재기를 끔`에서 실패하는 것은 트랙 "c1"이 따로 고치는 중이라 이 트랙의 실패로 세지 않는다(나오면 적기만).
7. **앱은 그대로인가**: `962e5fc`와 지금 것으로 각각 빌드한 `dist/net-workshop.html`의 해시가 같은지(검사 파일만 바뀌었으므로 같아야 한다).
8. **새로 생긴 문제**, 느리게 하기에서 찾은 앱 쪽 문제(검사가 아니라 화면이 틀리는 것).

## 형식과 끝나면

덧붙이는 절: 판정 줄(통과 = 반드시 수정 0건 / 수정 필요), 테스트 결과 표, 느리게 하기 배수별 결과 표(`962e5fc` → 지금), 발견한 문제 표(심각도, 파일:줄, 재현 방법, 고칠 방향), 확인하지 못한 것(리눅스 CI의 실제 통과는 `main`에 올린 뒤에만 알 수 있다).

최종 답변 **8줄 이하**: 판정, 원인 확인, 느리게 하기 결과(`962e5fc`의 목록 → 지금), 검사의 뜻이 그대로인지와 회귀를 잡는지, 놓친 곳, 빌드 해시, 테스트 숫자, 새 문제와 심각도별 개수, "반드시 수정" 목록(파일:줄), 확인하지 못한 것. 직접 잰 것과 추정을 구분한다.

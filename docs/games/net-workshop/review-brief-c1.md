# Review 서브에이전트 지침: 파일 크기 검사 걷어내기 + 흔들리는 CI 검사 (트랙 "c1")

## 역할과 범위

- 너는 **Review** 담당이다. Build가 [build-brief-c1.md](build-brief-c1.md)에 따라 고친 두 가지를 **독립적으로** 확인한다. Build와 분리된 검토자다.
- **검토 결과는 새 파일 `docs/games/net-workshop/review-c1.md`에 쓴다**(트랙의 작업 폴더 안). 그 파일만 만든다. 커밋하지 않는다.
- 코드·테스트·다른 문서를 고치지 않는다. 커밋·브랜치 바꾸기·작업 트리를 바꾸는 git 명령 금지(읽기용은 된다). `npm install`·`npm ci`·내려받기 금지.
- **트랙의 작업 폴더에서만** 일한다(코디네이터가 프롬프트로 알려 준다). 검증 파일·복사본은 정해 준 scratchpad 폴더에만. Build의 scratchpad와 코디네이터의 `ci-flake/`는 근거로 삼지 않는다.

## 검토 대상

기준 `cd6a39c`(`main`)와 트랙 브랜치 `track/c1`의 마지막 커밋 사이의 변경 전부. Build가 고쳐도 되는 파일은 build-brief-c1.md의 목록이다 — **`src/**`가 한 줄이라도 바뀌었으면 범위 위반**이다. Build의 최종 보고는 코디네이터가 요약해 전한다 — **확인 대상이지 근거가 아니다.**

## 확인할 것

1. **범위**: `git diff cd6a39c..HEAD --stat`이 허용 파일 안인지. 재현용 코드(CPU 느리게 하기 등)가 저장소의 검사 파일에 남지 않았는지.
2. **크기 상한**: ⓐ 400 KB를 넘는 게임이 빌드되고 그 파일이 브라우저에서 열리는지(임시 폴더의 시험용 게임으로 직접) ⓑ **그 밖의 빌드 동작이 그대로인지** — 바깥 참조 검사(`findExternalRefs`)가 여전히 빌드를 멈추는지, 제목 글꼴 넣기, 로그의 크기 표시. 기준 `cd6a39c`와 지금 것으로 각각 빌드한 `dist/*.html` 세 파일의 해시가 같은지 ⓒ `MAX_FILE_BYTES`를 쓰는 곳이 남지 않았는지(`scripts/dev.mjs`·`scripts/new-game.mjs`·`scripts/lib/**`·테스트) — 개발 서버(`node scripts/dev.mjs`를 정해 준 포트로 잠깐)와 `npm run new`의 단위 검사가 여전히 도는지 ⓓ `tests/unit/build.test.js`에서 **지워지거나 약해진 단언**이 크기 상한 말고는 없는지, 새 검사가 "넘어도 빌드된다"를 실제로 고정하는지(크기 검사를 되살린 복사본에서 그 검사가 실패하는가).
3. **흔들리는 검사 (가장 중요)**: ⓐ 원인이 Build·코디네이터의 설명과 같은지 직접 확인(`.btn`의 들뜸과 가라앉는 시간, 포인터를 뗀 직후의 자리) ⓑ scratchpad에 푼 **기준 `cd6a39c` 복사본**에 CPU 느리게 하기(`Emulation.setCPUThrottlingRate`)를 넣어 실패가 재현되는지, **지금 것의 복사본**에서 4·8·12·20배 × `--repeat-each=10` 이상으로 실패 0인지(두 기기 모두). 실패가 남으면 어느 줄·어느 값인지 ⓒ **검사의 뜻이 그대로인지**: 기대값이 여전히 `toEqual(start)`(0.01px까지)이고, 재는 항목·순서·장면이 줄지 않았는지. 기다림이 "끝나지 않는 움직임" 때문에 시간 제한에 걸릴 길은 없는지(움직임 줄이기 설정, 무한 반복 애니메이션이 그 버튼 안에 있는지) ⓓ 앱 쪽 회귀를 여전히 잡는지 — 복사본의 `base.css`에서 일부러 머리 높이를 흔들거나(예: 켠 시계가 줄을 밀어내게) 연속 칸의 자리를 없애면 이 검사가 실패하는지 ⓔ Build가 "같은 종류"로 더 고친 곳·안 고친 곳의 판단이 맞는지, 놓친 곳이 있는지(느리게 하기로 `engine-features.spec.js` 전체와 `net-workshop.spec.js`를 한 번씩 돌려 느린 기기에서만 실패하는 검사 목록을 만든다 — 시간 제한만 넘긴 것은 따로 표시).
4. **테스트**: `npm test`, `npm run test:e2e -- --workers=3`, `E2E_WIDE_TEXT=font npm run test:e2e -- --workers=3`을 직접 실행(통과·실패·건너뜀). 기준 `cd6a39c`의 숫자(단위 184, 브라우저 232개 중 199 통과·33 건너뜀)와 견줘 달라진 것이 설명되는지.
5. **문서**: 고친 문장이 사실과 맞는지(크기 상한은 없어졌고, 한 파일로 묶기·바깥 참조 금지는 그대로). 남은 옛 문장 목록(`docs/games/**`·`STATUS.md`·`HANDOFF.md`·`CLAUDE.md`는 코디네이터가 고칠 것이라 목록으로만).
6. **새로 생긴 문제**.

## 형식과 끝나면

`review-c1.md`: 판정 줄(통과 = 반드시 수정 0건 / 수정 필요), 테스트 결과 표, 느리게 하기 배수별 결과 표(기준 → 지금), 발견한 문제 표(심각도: 반드시 수정 / 고치면 좋음 / 참고, 파일:줄, 재현 방법, 고칠 방향), 확인하지 못한 것(리눅스 CI의 실제 통과는 `main`에 올린 뒤에만 알 수 있다).

최종 답변 **8줄 이하**: 판정, 크기 상한(빌드 결과물 해시·남은 사용처·검사의 뜻), 흔들리는 검사(원인 확인, 기준과 지금의 느리게 하기 결과, 뜻이 그대로인지, 회귀를 잡는지), 느린 기기에서만 실패하는 다른 검사 목록, 테스트 숫자, 새 문제와 심각도별 개수, "반드시 수정" 목록(파일:줄), 확인하지 못한 것. 직접 잰 것과 추정을 구분한다.

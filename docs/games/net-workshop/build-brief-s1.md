# Build 서브에이전트 지침: S1 쌓기나무 바탕 + 1·2차시 (동시 진행 트랙 "blocks")

## 역할

너는 **Build** 담당이다. 승인된 6학년 계획([spec-grade6.md](spec-grade6.md))의 **S1** — 쌓기나무를 직접 쌓고·빼고·돌려 보는 무대와 조작, 그리고 교과서 1·2차시에 맞춘 두 차시 — 를 만든다. 사용자가 특히 요청한 것은 "교과서 학습에 맞추어서 **쌓기나무를 직접 입체적으로 다루어 볼 수 있게**"다. 다른 Build 서브에이전트가 **같은 때에 다른 폴더에서 5학년 직육면체 차시**를 만들고 있다 — 두 결과는 나중에 코디네이터가 `main`에 합친다. 검증은 별도 Review 서브에이전트가 한다.

1. **[common-rules.md](common-rules.md)** — 정육면체 차시를 만들며 정한 공통 규칙. 쌓기나무도 **같은 조건**으로 만든다.
2. **[spec-grade6.md](spec-grade6.md)** — 요약, 1-2절(6-2 3단원 교과서 흐름)·1-4절(용어 표), 2-1절·**2-4절(쌓기나무 차시·단계)**, **3절(쌓기나무를 직접 입체적으로 다루기 — 화면·조작 표·누르기와 끌기·위·앞·옆 보기)**, 4절(오개념·피드백)·5절(정답 노출 검토), 6절(기술 설계: 직접 투영 SVG, 데이터 모델, 판정 함수, 문제 만들기), 8절(보상), 9절(교실 기기·접근성), 10절(파일 구조), 11절(테스트 계획), 12절의 **S1 줄**, 15절(결정: 띄울 수 없다, 앱 이름 등)
3. [spec.md](spec.md) 17절(보기 조작 — `orbit.js`), 16-8·16-9·16-12(점수·직접 만드는 단계)
4. [docs/dev-guide.md](../../dev-guide.md), [docs/engine.md](../../engine.md), [docs/design/spec.md](../../design/spec.md)("종이 공방" 디자인)
5. 지금 코드에서 물려받을 것: `src/games/net-workshop/orbit.js`(보기 값), `main.js`(차시·단계 등록), `view3d.js`의 조작판·끌기 부분(같은 느낌으로), 엔진 `app.js`·`drag-drop.js`·`icons.js`

교과서 PDF는 읽지 않는다(계획에 이미 정리되어 있다). 교과서의 문장·그림·문제 수치를 옮기지 않는다 — 문제와 그림은 모두 새로 만든다. 용어는 1-4절 표 그대로("만든 모양", 위·앞·옆에서 본 모양, "옆"은 오른쪽, 숨겨진 쌓기나무 …).

## 만들 것 (spec-grade6 12절 S1 줄)

- **쌓기나무 바탕**: 데이터·판정 순수 함수(`blocks.js` — 높이 지도, 위·앞·옆에서 본 모양, 개수, 그림이 같아 보이는가 등 6절), 무대(`block-view.js` — 직접 투영 SVG, 원근 없는 그리기, 멈춘 그림, 층별로 벌려 보기), "위에서 본 판"(`block-pad.js` — 48px 칸, 키보드·버튼만으로 쌓기·빼기). 파일 이름·나눔은 10절을 따른다.
- **조작 전부(3절의 조작 표)**: 쌓기(바닥 칸·윗면·옆면을 짧게 누름, 놓일 자리 미리 보기), 빼기, 되돌리기, 모두 치우기, **쌓는 중에도 끌어서 돌리기**(8px 문턱, `orbit.js` 방식 그대로 — 끝없이·0.5~2배·조작판), [위][앞][옆] 그 방향에서 보기, 크게·작게, 처음 보기로. 마우스·터치·키보드 각각. 판은 3×3칸·3층, **공중에 띄울 수 없다**(놓으면 아래로 내려앉음).
- **1차시 `blocks-look` 어느 방향에서 보았을까**(교과서 56~57쪽): `blocks-play`(쌓기 놀이터 — 조작 익히기) · `blocks-where` · `blocks-scene`
- **2차시 `blocks-top` 만든 모양과 위에서 본 모양**(58~59쪽): `blocks-copy` · `blocks-count` · `blocks-hidden`
- 단계 내용·문항 수·돌려 보기 잠금·끝나는 조건은 2-4절 표 그대로. 아이콘은 엔진 `icons.js`에 덧붙인다.
- **지금 구조에 차시로 넣는다**: 영역 고르는 화면·여러 파일 빌드·앱 이름 바꾸기(B0)는 아직 하지 않았고 **이번 범위가 아니다**. 두 차시를 지금의 "차시 묶음"으로 등록해 단계 지도에 정육면체 차시 뒤에 보이고 `?lesson=blocks-look`·`?lesson=blocks-top`으로 바로 들어가게 한다. 계획의 "S1은 B0에 기댄다"는 것은 영역 화면·늦게 불러오기뿐이므로, 그것 없이도 되게 만들고 나중에 B0가 입히기 쉽게(쌓기나무 코드를 전개도 코드와 떨어진 파일들에) 둔다.
- 계획에 적히지 않은 세부는 계획의 뜻과 공통 규칙에 맞게 네가 정하고 까닭을 보고한다. 사용자가 정해야 할 만큼 큰 갈림길은 추측하지 말고 "사용자 결정 필요"로 적는다. 계획이 "임시"·"확인 필요"·"계산값"이라고 적은 것(화면 배치, 쌓기나무 한 변의 크기, 차시 시간, 문항 수)은 직접 만들어 보고 잰 값으로 확정해 보고한다.

## 반드시 지킬 것

- [common-rules.md](common-rules.md) 전부. 쌓기나무에서 특히:
  - **답하기 전 정답 노출 0**(5절): 돌려 보면 답이 보이는 문항(방향 맞히기·개수·"이쪽에서 보면")은 답하기 전에 그 그림을 돌릴 수 없다. 내 판은 늘 돌릴 수 있다. 내 쌓기의 2D 그림은 [확인하기] 뒤에만. 문항이 달라도 답하기 전 화면의 속성·클래스·알림에 답이 없다.
  - **누르기와 끌기를 헷갈리지 않는다**: 8px 문턱, 끌기 뒤 따라오는 click 막기와 풀기, 끄는 동안 브라우저가 화면 쓸기로 받지 않게(관성 스크롤 → 첫 탭 삼킴 방지). 쌓기나무는 "쌓는 중에도 돌리는" 무대라 이 구분이 가장 중요하다 — 돌리려다 쌓이거나 쌓으려다 돌아가는 일이 없게, 마우스·터치 각각 직접 재서 보고한다.
  - 판정을 **독립 계산과 전수 비교**: 3×3칸·3층 높이 지도 262,144개 전부에서 위·앞·옆 모양, 개수, "같아 보이는가", 문제 후보의 "쌓기가 하나로 정해지는가"(계획의 수치 56,478 / 39,041 / 17,437 / 12,636과 견줌).
  - 점수: 엔진 규칙 안에서. 놀이터(`blocks-play`)는 채점 없음. 쌓는 단계는 맞힐 때까지 다시 하고 틀린 시도도 기록. 일부러 틀려 이득 0·화면 = 저장·되풀이로 쌓이지 않음을 독립 계산과 견주는 무작위 검사.
  - 1366×768·1366×680·820×1180 세로·가로 스크롤 0, 판 안쪽 넘침 0, 플레이 도중 머리·매트 움직임 0, 48px, 키보드만으로 쌓기·빼기·돌리기·확인, 색만으로 구분하지 않음, 움직임 줄이기·`?fx=low`, 화면 읽기 이름·알림(쌓은 개수, 보는 방향).
  - 그리기: 깊이 순서 오류 0(광선 계산과 견줌 — 계획 6-1의 방법), 느린 CPU에서도 끊기지 않음, 누른 곳이 가리키는 쌓기나무·면이 정확함(보기 여러 가지 × 모든 면).
- **정육면체 차시와 도전 주문서의 화면·점수·기록은 한 글자도 달라지면 안 된다.** 지금 있는 단위·브라우저 검사는 고치지 않고 통과해야 한다 — 단, **전체 단계 수·차시 수를 세는 기존 검사는 차시별로 세도록** 고쳐 다른 트랙이 차시를 더해도 깨지지 않게 한다(이유를 보고).
- 테스트: `npm test` + `npm run test:e2e -- --workers=4`(보통) + **글꼴 흉내 모드**(`E2E_WIDE_TEXT=font npm run test:e2e -- --workers=4`)에서 실패 0. 글자 폭에 기대는 픽셀 상수를 쓰지 않는다.

## 동시에 만드는 동안 지킬 것 (common-rules 10절)

- **네 작업 폴더와 브랜치에서만** 일한다(코디네이터가 프롬프트로 알려 준다). `main` 체크아웃(`/Users/sungchul/Desktop/play2/game2`의 맨 위 폴더)과 다른 트랙의 폴더는 읽기도 고치기도 하지 않는다.
- 쌓기나무의 코드·스타일·테스트는 **새 파일**에 둔다(10절의 파일들, `tests/unit/net-workshop-blocks*.test.js`, `tests/e2e/net-workshop-blocks.spec.js`). 같이 쓰는 파일(`main.js`의 차시·단계 등록, `style.css`, `tests/e2e/net-workshop.spec.js`, 엔진 `icons.js`, `docs/engine.md`)은 **덧붙이기만, 최소로** — 있는 줄의 순서를 바꾸거나 다시 쓰지 않는다. **전개도 공통 부품(`fold.js`·`geometry.js`·`view3d.js`·`free-board.js`·`play-*.js`·`logic.js`의 전개도 부분)은 고치지 않는다**(직육면체 트랙이 지금 고치고 있다). `orbit.js`는 읽어 쓰기만 하고, 고쳐야 하면 고치지 말고 보고한다.
- 엔진(`src/shared/**`)은 꼭 필요한 만큼만 고치고 무엇을 왜 바꿨는지 보고한다. 아이콘·목록은 끝에 덧붙인다.
- 커밋은 **자기 브랜치에만** 한다(작업 단위마다 커밋해도 된다). `git push`·`main`에 합치기·다른 브랜치 바꾸기는 하지 않는다. 최종 상태는 커밋해 둔다(Review가 그 커밋을 본다).
- 이 폴더에서 `npm ci`는 처음 한 번 해도 된다. Playwright 브라우저는 이미 깔려 있다(1.56.1).
- 개발 서버는 정해 준 포트만. 5173·5183은 건드리지 않는다. e2e는 `--workers=4`. 시간 제한으로 실패한 검사는 혼자 다시 돌려 부하 탓인지 가린다.
- 임시 파일·스크린샷은 정해 준 scratchpad 폴더에만(계획 때의 시제품·측정 스크립트는 `scratchpad/plan-grade6/`에 있다 — 참고용). 작업 폴더 안에 임시 파일을 남기지 않는다.

## 고쳐도 되는 파일

- `src/games/net-workshop/`의 **새 쌓기나무 파일들**과 `main.js`·`style.css`(덧붙이기), `tests/unit/net-workshop-blocks*.test.js`·`tests/e2e/net-workshop-blocks.spec.js`(새 파일), `tests/e2e/net-workshop.spec.js`(단계 수를 세는 검사만)
- 엔진은 필요한 만큼만: `src/shared/**`, 그 테스트, `docs/engine.md`
- 고치지 않는 것: 전개도 공통 부품(위), `docs/games/**`·`docs/design/**`·`docs/HANDOFF.md`·`docs/dev-guide.md`, `CLAUDE.md`, 예시 게임·템플릿, `tests/e2e/smoke.spec.js`·`sample-divisor-sort.spec.js`, `tests/e2e/helpers.js`·`playwright.config.js`, `scripts/**`, package 파일, `.github/**`, `.claude/**`. 앱 이름·빌드 구조·영역 화면(B0)·쌓기나무 3~5차시(S2·S3)·각기둥·원기둥은 건드리지 않는다.

## 끝났다의 기준

`npm test`, e2e 보통·글꼴 흉내 모두 실패 0(마지막 커밋에서 처음부터). 3절의 조작 표를 네 수단(마우스·터치·키보드·버튼)으로 끝까지, 정답 노출 검사, 판정 전수 비교, 두 차시를 브라우저에서 처음부터 끝까지 직접 해 보고 걸린 시간 기록, 네 크기 스크린샷을 직접 열어 확인(쌓기나무가 또렷하고 방향 글자 "앞"·"옆"이 읽히는지, [위][앞][옆]에서 2D 그림과 똑같이 보이는지). 정육면체 차시가 기준 커밋과 같음을 수치로.

## 최종 보고 (16줄 이하)

만든 것(바탕·조작·두 차시 여섯 단계)과 직접 확인한 방법·잰 값, 누르기와 끌기를 가르는 방식과 잘못 쌓임·잘못 돌아감을 잰 수치, 계획의 계산값을 잰 값으로 확정한 것(쌓기나무 크기·배치·문항 수·차시 시간), 판정 전수 비교 수치, 정답 노출 수치, 점수, 네 크기 배치 수치, 그리기 성능·깊이 순서, 정육면체 차시 불변 수치, 테스트 결과(보통·글꼴 흉내), 엔진에서 바꾼 것, **같이 쓰는 파일에서 고친 곳 목록(합칠 때 부딪힐 수 있는 곳)**, 계획과 다른 점, 사용자 결정이 필요한 것, 남은 한계, 마지막 커밋 해시. 직접 실행해 확인한 것과 추정을 구분한다.

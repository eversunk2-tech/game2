# Build 서브에이전트 지침: B0c 게임 인트로 화면 (트랙 "b0")

## 역할

너는 **Build** 담당이다. 사용자의 수정 요청([spec-grade6.md](spec-grade6.md) **15-6**)에 따라, 앱을 열면 맨 처음 보이는 **게임 인트로 화면**을 만든다. [입장하기]를 누르면 B0a가 만든 **학년 고르기 화면**으로 간다. 검증은 별도 Review 서브에이전트가 한다.

사용자의 말: "메인 페이지를 학생들이 공부하고 싶은 마음이 들 수 있는 재미있는 도형 게임 느낌으로 해서 최근 유행하는 게임 인트로 화면처럼 만들어줘. 캔바 연계하여 디자인하는 방향으로 하면 되겠어. 메인 인트로 화면에서 '입장하기'를 누르면 학습 카테고리로 이동하도록 해줘" — 그리고 참고 이미지 셋을 보이며 "조금 더 이런 진짜 게임 느낌으로". 캔바 쓰는 방식은 사용자가 정했다: **캔바 그림 + 코드 움직임**.

## 그림 (사용자가 캔바 시안에서 골라 내려받음 — 이미 저장소에 있다)

- `src/games/net-workshop/img/intro-bg.jpg` — 1680×944. 밝은 낮의 하늘 아래 도형 모양 건물들의 마을, 왼쪽에 소년, 오른쪽에 소녀(빛나는 전개도를 들고 있음), 가운데 위는 비어 있는 하늘, 가운데 아래는 계단.
- `src/games/net-workshop/img/intro-title.webp` — 1352×873, 투명 바탕. 황금빛 입체 글자 "입체도형 공방"(두 줄), 왼쪽에 금빛 정육면체, 오른쪽에 금빛 전개도, **아래에 빈 파란 리본**(높이의 아래쪽 약 20% — 부제를 얹을 자리).
- 그림 파일은 고치지 않는다(자르기·색 바꾸기 금지). 다른 그림을 더 쓰려면 코드(SVG·CSS)로 그린다. 바깥 주소·웹 글꼴 금지(지금 빌드는 CSS `url()`의 그림을 HTML 안에 넣는다 — JS에서 그림 파일을 import하지 않는다, dev-guide).

## 만들 것

- **인트로 화면**: 화면 가득 배경 그림(`cover`, 화면 비율에 따라 잘리는 자리를 정한다 — 세로 화면에서도 하늘과 두 아이가 되도록 보이게), 가운데 위에 제목 그림(가로 화면에서 화면 너비의 약 45~55%, 세로 화면에서 약 85%), 제목 리본 위에 부제 **"전개도와 쌓기나무로 떠나는 도형 모험"**(제목 글꼴, 흰 글자 + 짙은 남색 테두리, 리본 안에 들어가게 — 화면 크기마다 맞춤), 아래 가운데 계단 위에 큰 **[입장하기]** 버튼(게임 느낌: 두껍고 반짝이는 버튼 — 금빛·파란 그러데이션, 짙은 남색 테두리, 아래 그림자, 48px보다 훨씬 크게).
- **움직임(최근 게임 인트로처럼)**: 처음에 제목이 위에서 툭 떨어져 살짝 튀고(0.6초 안팎), 부제·버튼이 이어서 나타난다. 그 뒤로 제목은 천천히 떠오르내리고 가끔 빛이 한 번 스쳐 지나가며, 제목 둘레·하늘에 작은 별 반짝임, [입장하기]는 숨 쉬듯 커졌다 작아진다. 화면 아래에서 작은 정육면체·직육면체 조각이 천천히 떠오르는 것도 좋다(코드로 그림). **움직임 줄이기(`prefers-reduced-motion`)와 `?fx=low`에서는 움직이지 않는 한 장면**. 움직임은 GPU에 맡기는 `transform`·`opacity`만 쓰고, 느린 크롬북에서도 끊기지 않게(느린 CPU 흉내로 잰다).
- **소리**: [입장하기]를 누르면 짧은 효과음(엔진 `ctx.sfx` 또는 같은 것 — 소리 끔이면 없음). 오른쪽 위에 지금의 소리 켜고 끄기 버튼.
- **언제 보이나**: 주소에 `?grade=`·`?area=`·`?lesson=`·`?stage=`가 없을 때 앱을 열면 인트로부터. 선생님이 준 수업 주소로 들어오면 인트로 없이 그 화면으로. 학년 고르기 화면에서 [처음으로]를 누르면 인트로로 돌아간다. (매번 보여 주는 것이 수업에 걸림돌이 되면 "한 번 본 뒤로는 짧게" 같은 것은 사용자에게 물어 정한다 — 이번에는 매번 보인다.)
- **[입장하기] → 학년 고르기**(B0a의 처음 화면을 그대로 쓴다. 학년 고르기 화면의 머리에도 앱 이름 대신 작은 제목 그림을 써도 된다 — 네가 정해 보고).
- **엔진 기능으로**: 게임 정의의 선택 값(예: `intro: { subtitle, enterLabel }`, 그림은 게임 CSS가 클래스로 준다)로 켠다. **`intro`가 없는 게임(예시 게임, 템플릿, 시험 페이지)은 한 글자도 달라지지 않는다.**
- **접근성**: 인트로에 화면 읽기용 제목(`h1` "입체도형 공방" — 그림의 대체 글), 배경은 꾸밈(`aria-hidden`), [입장하기]는 진짜 버튼이고 처음 초점이 간다(Enter·Space). 부제는 글자(그림이 아님). 대비: 부제·버튼 글자가 배경 위에서 4.5:1.
- **처음 여는 시간**: 지금 빌드는 그림을 HTML 안에 넣으므로 `net-workshop.html`이 약 0.5 MB 커진다(B0b에서 파일로 나간다). 그림이 풀리기 전에는 하늘색 그러데이션을 먼저 보이고 그림이 준비되면 부드럽게 바꾼다(빈 화면 0). 처음 화면이 그려지는 시간을 spec-grade6 7-2절과 같은 방법(로컬, 보통·6배 느린 CPU)으로 재서 보고한다.

## 반드시 지킬 것

- [common-rules.md](common-rules.md) 전부. 네 크기(1366×768·1366×680·820×1180·390×844)에서 세로·가로 스크롤 0, 제목·부제·버튼이 잘리지 않고 겹치지 않음, 버튼이 두 아이의 얼굴을 가리지 않음(스크린샷을 직접 열어 본다), 1024×768·1180×820(가로 태블릿)도. 글꼴 흉내에서 부제가 리본 밖으로 나가지 않음.
- **그 밖의 화면은 그대로**: 학년 고르기 화면부터 뒤(B0a가 만든 것)와 모든 플레이 화면·점수·기록·수업 주소로 연 화면의 차이 0. 예시 게임 차이 0. 저장 열쇠·모양 그대로.
- 브라우저 검사는 처음부터 느린 기기를 견디게(움직임이 끝난 뒤에 재기 — 인트로는 계속 움직이므로 **움직임 줄이기로 연 화면에서 배치를 재고**, 움직이는 화면에서는 "보이는가·누를 수 있는가"만), `waitForTimeout`·`retries` 금지, 혼자 3초 넘는 검사에 `test.setTimeout`. 끝내기 전에 CPU 느리게 하기(4·8·12배)로 새 검사 값 실패 0.
- 처음 화면을 거쳐 가던 기존 검사(B0a가 학년 카드를 거치게 고친 것)는 인트로를 거치게 고친다 — 뜻은 그대로, 고친 곳과 이유를 표로. 기존 검사를 지우거나 약하게 만들지 않는다.
- 테스트: `npm test`, `npm run test:e2e -- --workers=4`, `E2E_WIDE_TEXT=font npm run test:e2e -- --workers=4` 모두 실패 0.

## 고쳐도 되는 파일

- 엔진: `src/shared/ui/app.js`(인트로 기능), `src/shared/styles/base.css`(인트로·버튼 꾸밈 — 다른 화면의 토큰은 바꾸지 않는다), 필요하면 `src/shared/core/**`, 그 테스트, `docs/engine.md`(2·8절)
- 게임: `src/games/net-workshop/main.js`(인트로 값 — 덧붙이기), `style.css`(그림 클래스), `index.html`(필요하면 `<link rel="preload">` 같은 것만)
- 검사: 새 파일 `tests/e2e/net-workshop-intro.spec.js`, 처음 화면을 거치는 기존 검사(`tests/e2e/*.spec.js` — 거치는 줄만), `tests/unit/` 아래 엔진 검사
- 고치지 않는 것: `img/` 그림 파일, `scripts/**`, `tests/e2e/helpers.js`·`playwright.config.js`, 플레이 코드(`fold.js`·`view3d.js`·`play-*.js`·`cuboid-*.js`·`blocks/**` 등), `docs/games/**`·`docs/STATUS.md`·`HANDOFF.md`·`design/**`·`dev-guide.md`, `CLAUDE.md`, 예시 게임·템플릿의 코드, package 파일, `.github/**`, `.claude/**`

## 지킬 것

- 작업 폴더·브랜치·scratchpad·포트는 코디네이터가 프롬프트로 알려 준다. 커밋은 그 브랜치에만, 푸시·합치기 금지. `npm install`·`npm ci`·내려받기 금지. 띄운 실행·서버는 모두 내리고 끝낸다.
- 계획에 적히지 않은 세부(움직임의 시간, 버튼 색, 부제 자리)는 사용자의 말과 참고 이미지의 분위기(밝고 반짝이는 진짜 게임 인트로)에 맞게 네가 정하고 보고한다. 사용자가 정해야 할 만큼 큰 갈림길은 "사용자 결정 필요"로 선택지와 추천을 붙여 적는다.

## 끝났다의 기준

세 가지 테스트 실패 0(마지막 커밋에서 처음부터), 느린 기기 값 실패 0, 네 크기 + 가로 태블릿 스크린샷을 직접 열어 확인(움직임 줄이기 한 장, 움직이는 중 한 장), 인트로가 움직이는 짧은 기록(스크린샷 여러 장)으로 끊김 없음, 처음 여는 시간, 그 밖의 화면·예시 게임 불변 수치.

## 최종 보고 (14줄 이하)

만든 것(배치·움직임·소리·언제 보이나·엔진 선택 값)과 직접 확인한 방법·잰 값, 네 크기 배치 수치(스크롤·겹침·리본 안 부제), 움직임 줄이기·`?fx=low`, 접근성, 처음 여는 시간(보통·6배 느린 CPU)과 HTML 크기, 그 밖의 화면·예시 게임 불변, 느린 기기, 테스트 결과(보통·글꼴 흉내), 고친 기존 검사와 이유, 엔진에서 바꾼 것(줄 번호), 네가 정한 세부, 사용자 결정이 필요한 것, 남은 한계, 마지막 커밋 해시. 직접 실행해 확인한 것과 추정을 구분한다.

## 덧붙임 (2026-10-16, B0a Review 뒤 코디네이터)

- **바탕**: B0c는 `main`에 영역 화면(B0a, Review 통과)과 쌓기나무 3·4차시(S2 — Review가 통과하면)가 합쳐진 뒤 그 위에서 만든다.
- **처음 화면을 거치는 검사를 모두 이번에 고친다 — 쌓기나무 검사도**: B0a 때문에 이미 깨진 쌓기나무 검사가 있다(`tests/e2e/net-workshop-blocks.spec.js`의 "단계 지도: 쌓기나무 네 차시가…"(S2 전에는 "두 차시"), "1차시(?lesson=blocks-look)…", "2차시(?lesson=blocks-top)…", "접근성: …"(나간 뒤 '단계를 골라요'를 봄) — 옛 [시작하기]·한 줄 단계 지도·처음 화면 놀이 방법을 전제로 한다). 인트로가 들어가면 처음 화면이 다시 바뀌므로 **이 검사들도 B0c가 인트로 → 학년 카드 → 영역 → 단계 지도 구조에 맞게** 고친다(쌓기나무 영역 안 차시 칩은 "1차시…", 놀이 방법은 영역 지도에서). 고칠 수 있는 파일에 `tests/e2e/net-workshop-blocks.spec.js`(처음 화면을 거치는 그 검사들의 줄만)를 더한다. 뜻은 그대로 두고, 고친 곳과 이유를 표로.
- **차시가 하나뿐인 영역의 차시 칩**(B0a Review의 B0a-2, 코디네이터 결정): 영역 지도에서 직육면체가 "1차시", 수업 주소에서는 "2차시"로 보여 헷갈린다. **차시가 하나뿐인 영역(정육면체·직육면체, 나중의 원기둥 등)의 영역 지도에서는 차시 칩을 보이지 않는다**(차시 제목만). 차시가 둘 이상인 영역(쌓기나무)은 그대로 "1차시…". 수업 주소 화면은 바꾸지 않는다.
- **(할 수 있으면) B0a-1**: 960×680·1024×600의 글꼴 흉내에서 처음 화면이 12·75px 넘친다(필수 크기 밖). 인트로가 들어가며 처음 화면이 바뀌므로, 학년 고르기 화면에서 이 두 크기도 넘치지 않게 한다. 못 하면 잰 값만 보고.
